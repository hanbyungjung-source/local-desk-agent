# Local Desk

## Kaggle T4 두 장 API

2026-09-27: [T4 엔진 연구](KAGGLE-T4-ENGINE.md) 결과로 `kaggle_server.py`를 **llama.cpp v0.5.0 + 텐서 분할 + 본체 MTP(초안3) + 검증 MMQ(`GGML_CUDA_MMVQ_MAX_BATCH=1`)**로 바꿨다. 같은 세션 b11000 대비 생성 +58%(고정 4사례 37.18 t/s)이며, 운영 경로 드라이런에서도 4사례가 모두 통과했다(38.67 t/s). 별도 MTP 파일(1.37GB)은 더 이상 받지 않는다. 2026-09-29 새 운영 노트북 `notebookb11c5a2f1f`(비공개)에 반영했고(버전 2), 실제 세션에서 앱 클라이언트 텍스트·이미지와 고정 4사례(34.12 t/s, 드라이런과 답변 동일)를 확인했다. 노트북 Persistence는 **Files only**여야 한다. `/kaggle/working/local-desk-cache/`의 빌드 캐시가 맞으면 약 25분 걸리는 llama.cpp 빌드를 건너뛴다(`BUILD_CACHE_HIT`). 모델은 용량 때문에 매 세션 다시 받는다(약 1분32초). 이전 판(b11000·층 분할 `36,30`·별도 MTP)은 기존 노트북 v5에 그대로 남아 있다. 아래 하드웨어·배치 설명 중 b11000·층 분할·별도 MTP 부분은 이전 판 기록이다.

2026-09-26: 개인용 OpenAI 호환 API를 **ngrok 고정 주소, 192K(196,608토큰), MTP 초안3토큰, GPU 비전 유지**로 연결했다. 검색 API 연동은 보류 상태다. 아래 localhost.run 주소와 장애 사례는 고정 터널 전환 전 기록이다.

- 앱을 다시 열고 API 설정에서 `Kaggle T4x2 Qwen3.8 Q4 MTP` 프로필을 불러온 뒤 API 백엔드를 적용한다. 기존 로컬 모델 선택과 다른 프로필은 변경하지 않았다.
- 모델 ID: `qwen3.8-27b-ud-q4-k-xl`. 고정 API 주소는 `https://<NGROK_DOMAIN>/v1`이며 실제 요청 경로는 `/v1/chat/completions`다.
- Kaggle 노트북(비공개)의 실행 세션이 살아 있어야 한다. 추론 API 키는 Kaggle Secrets의 `LOCAL_DESK_API_KEY`와 앱의 Windows DPAPI 저장소를 사용한다. ngrok용 `NGROK_AUTHTOKEN`은 별도 자격 증명이며 Kaggle Secrets에 등록하고 PC API 키로 입력하지 않는다. `NGROK_DOMAIN`에는 계정의 고정 도메인을 등록한다. 짧은 API 키는 `allow_short_key=True`를 명시해야만 허용된다.
- Qwen3.8-27B UD-Q4_K_XL 약17.6GB, 별도 MTP 약1.37GB, F16 비전 프로젝터 약928MB를 같은 고정 리비전에서 다운로드하고 SHA256을 검사했다. llama.cpp b11000, CUDA12.8, T4용 `sm75` 빌드다.
- 두 T4에 layer split `36,30`, MTP `draft-mtp`/초안3토큰/CUDA1, 문맥196,608, 본체 KV Q8, 동시 슬롯1, batch512/ub128, `--fit off`를 사용한다. 기본 언어층 배치 의도는 GPU0의0~35층, GPU1의36~63층이며 출력층과 MTP는 별도다. 신규 앱 프로필은 xhigh, 스트리밍, 출력 토큰 상한 없음(`max_output_tokens=-1`), 요청10,800초(3시간), 자동 재시도0이다. 기존 프로필의 출력 한도와 요청 시간은 재연결 시 보존하므로 `Generation`의 `max_output_tokens`와 `timeout_seconds`에서 변경한다. 로컬 전용 사고 예산 설정은 외부 API 프로필에 자동 적용되지 않는다.
- 240K는 MTP 계산 버퍼 할당 실패, 216K는 준비 응답 이후 비전 계산 버퍼 할당 경고가 있어 최종192K를 선택했다. 최종 시작 관측에서 GPU 여유는 각각775/897MiB였으며 최대 부하의 여유를 보장하는 값은 아니다.
- 최종192K에서 실제 앱 `APIClient`의 HTTPS 스트리밍 텍스트 응답 `READY192`가4.938초, 1280x720 파란 이미지 판독이11.969초에 통과했다. 첫 토큰은 각각2.766/6.922초였다. [검증 기록](data/kaggle-192k-validation.json)에 결과를 보존했다. 전체192K 입력, 장시간 부하, 전체 데스크톱 자동화, MTP OFF 대비 가속률은 검증하지 않았다.

### ngrok 고정 터널

사용자가 선택한 무료 ngrok 계정의 dev domain을 명시해 시작한다. `NGROK_DOMAIN=<NGROK_DOMAIN>`이며 다른 주소로 자동 전환하지 않는다. 첫 시작에 Kaggle에서 pyngrok8.1.2와 공식 배포 ngrok 실행 파일을 준비한다. 이번 검증의 실행 파일은3.39.11이었다. PC에 ngrok이나 모델을 설치할 필요는 없다.

`start_tunnel()`은 로컬 모델의 인증 거부·정상 키·모델 ID를 확인한 뒤 고정 도메인을 연다. ngrok 인증 토큰은 해당 자식 프로세스의 환경 변수로 전달하고 명령줄·설정 파일·출력에 넣지 않는다. 모델 API 키와 Kaggle 환경 변수는 ngrok 자식에서 제외한다. 로컬 제어 API는127.0.0.1:4040에만 열고 요청 내용 검사는 `--inspect=false`로 끈다. 해당 포트에 실행 중인 에이전트가 있으면 중복 시작을 거부한다. 공개 URL과 PID는 `fixed-tunnel.json`에 기록한다.

새 주소에서 키 없는 요청401, 정상 인증 모델 조회, 실제 APIClient의 SSE 응답1회를 검증했다. 서로 다른 텍스트 상태22개, 총7.594초였으며 연결 확인이지 성능 대조가 아니다. 모델 PID·192K·MTP3·GPU 배치는 그대로 유지했다. [연결 검증 기록](data/ngrok-connection-validation.json)을 보존했다. 새 세션·장시간 네트워크 장애 후 복구까지 반복 검증한 것은 아니다.

[ngrok 무료 플랜](https://ngrok.com/docs/pricing-limits/free-plan-limits/)은 현재 월 전송량1GB·HTTP 요청20,000회 한도가 있다. 계정 dev domain은 고정이지만 네트워크·계정 한도·Kaggle 세션 종료까지 막아주지는 않는다. ngrok이 TLS를 처리하므로 민감한 자료 전송에 유의한다. 계정 가입·요금제 업그레이드나 추가 도메인 구매는 자동으로 하지 않는다.

### MTP 고정 기본값 비교

2026-09-26 사용자 요청으로 MTP 길이3과2를 각각 고정한 새 서버에서 한 번씩 비교했다. 동적 길이 전환은 구현하지 않는다. 같은192K·분배36,30·본체Q8 KV·batch512/ub128·xhigh를 유지하고, 공통 지침과 엄격한 도구 스키마를 포함한 네 입력의 해시를 고정했다. 비교 요청은 temperature0·seed42·출력한도4096이며, 운영 서버의 샘플링 기본값은 바꾸지 않았다.

| 항목 | MTP 3 | MTP 2 |
|---|---:|---:|
| 텍스트 복사 | 11.607초 | 12.613초 |
| 계산 | 6.992초 | 7.468초 |
| 이미지 판독 | 9.015초 | 9.317초 |
| 예열 제외 합계 | **27.614초** | 29.398초 |
| 생성 속도 합산 | **21.26 t/s** | 19.76 t/s |

세 항목 모두 같은 정답·입력 토큰·캐시·출력 토큰 수(238/125/69)였고, 각 길이의 별도 예열도 통과했다. 예열 제외 총 응답 시간이약6.1% 짧은 **MTP 3을 고정 기본값으로 유지**하고 실제 서버도3으로 복구했다. 생성 속도는 서버 규칙에 맞춰 각 응답의 첫 토큰을 제외한 수를 생성 시간 합계로 나눈 값이다. 초기 집계는 보존하고 [보정 비교 결과](data/kaggle-mtp-fixed-20260926/v2/comparison-v2.json)를 별도로 기록했다.

실행 순서는3→2이며 반복·무작위 순서·전체192K 입력·장시간 안정성 검사는 하지 않았다. 단회 합성 입력 결과이지 모든 실제 작업에서6.1% 향상을 보장하는 값은 아니다. 실행 중 표본의 GPU 여유 최저는3에서701/881MiB, 2에서785/947MiB였고 RAM 가용량 검사도 통과했다. 최초 재시작은 TCP TIME_WAIT를 포트 점유로 판단한 사전 검사에서 막혀 추론0건으로 보존했다. 포트 검사에 주소 재사용 옵션을 추가한 뒤 실제 Linux에서 활성 리스너 차단을 확인하고 별도 결과 폴더에서 진행했다. 모델·자원·입력 원자료는 [검증 기록](data/kaggle-mtp-fixed-20260926/v2/audit.json)에 있다.

Windows RX580용 Vulkan 연구 최적화를 이 CUDA 서버에 적용한 것도 아니다. [시작 로그·빌드 근거](data/kaggle-mtp-fixed-20260926/v2/optimization-inventory.json)를 보존했다.

192K는 속도 최적화 자체가 아니라 큰 문맥 용량을 위한 선택이다. 남은 주요 검증은 실제 긴 작업의 CPU 샘플링·GPU 대기 비용, RAM 문맥 캐시의 재사용 효과와 메모리 비용, 장문에서의 처리량이다. ub128·입력·사고 설정을 임의로 줄이거나 새 성능 시험을 자동 시작하지 않았다.

### PC 원클릭 연결

Kaggle 서버를 켠 뒤 PC에서 [start-kaggle.bat](start-kaggle.bat)를 더블클릭한다. 기존 Local Desk가 열려 있으면 먼저 완전히 종료해야 한다. 기존 Python 환경을 사용하며 모델을 PC에 다운로드하거나 PC 추론 서버를 실행하지 않는다.

- 저장된 Kaggle 주소와 암호화 키가 있으면 자동으로 연결을 확인하고 해당 API 프로필을 적용한 뒤 앱을 연다.
- 처음 사용하거나 주소가 만료되면 입력 창에서 최신 `API_URL`을 넣는다. API 키는 마스킹 입력이며, 비워 두면 기존 Kaggle 프로필의 키를 재사용한다. 새 키가 필요할 때만 Kaggle Secrets와 같은 값을 직접 입력한다.
- 확인은 인증된 `GET /v1/models` 한 번으로 수행하며 모델 추론을 요청하지 않는다. 리디렉션을 따라가지 않고 HTTPS의 ngrok 무료 고정 도메인과 이전 localhost.run 주소만 허용한다. 입력한 주소로 키가 전송되므로 본인 계정의 주소인지 확인한다. ngrok 전송에는 공식 안내의 `ngrok-skip-browser-warning` 헤더를 사용한다.
- 확인 성공 후 문맥196,608의 Kaggle 프로필과 API 백엔드를 선택한다. 다른 프로필, 로컬 모델, 도구 권한, 자동 요약 설정은 유지한다. 최초 변경 전 설정은 `data/settings.before-kaggle-connect.json`에 보관한다.
- 인증 실패 시 설정을 저장하지 않는다. 연결 확인 중 취소가 확인되면 저장하지 않으며, 취소 후 앱을 열지 않는다. 저장을 마친 직후의 취소는 이미 저장한 설정을 되돌리지 않는다. 키는 기존 Windows DPAPI 저장소를 사용하며 배치파일·명령 인자·설정 JSON에 넣지 않는다.

Kaggle 세션 시작·종료는 여전히 노트북에서 직접 수행한다. PC 배치가 세션을 자동으로 켜거나 새 터널 주소를 원격 조회하지는 않는다. 기본 [start.bat](start.bat)는 종전대로 현재 저장 설정으로 앱만 연다. 별도 Python 경로가 필요하면 `start-kaggle.bat -PythonPath "사용할 환경의 python.exe 경로"`로 지정한다. 실행 후 오류 로그는 `data/launcher`에 남는다.

연결 창은 이제 인증 오류 `HTTP 401/403`, 터널·서버 연결 오류 `HTTP 502/503/504`, 네트워크 오류를 구분한다. 원격 응답 본문이나 키 값은 표시하지 않는다. 2026-09-26에는 PC에서503이 발생했지만 Kaggle 내부 서버는200이었고 SSH 터널만 종료된 사례를 확인했다. 모델 재시작 없이 터널을 새로 열어 PC의 인증된 모델 목록 조회가 통과했다. 이 확인은 모델 추론이나 장시간 터널 안정성 검사가 아니다.

이전 localhost.run 연결에서 `API HTTP 503; retry limit reached (1 request(s))`가 발생했다. 재시도 설정0이면 최초 요청 한 번으로 중단했다는 뜻이다. 503 본문의 `no tunnel here`가 확인되면 최신 URL 갱신 안내를 덧붙이되 본문은 표시하지 않는다. 같은 SSH 프로세스가 살아 있어도 주소가 바뀌는 문제 때문에 현재는 ngrok 고정 주소로 전환했다. 자동 재시도0과 사용자 작업 기록은 변경하지 않았다. 고정 주소에서도 에이전트 종료·서비스 장애·계정 한도로 접속이 실패할 수 있다.

### Kaggle 서버 시작

1. Kaggle 노트북에서 가속기를 **T4 x2**, Internet을 켜고, Secrets의 `LOCAL_DESK_API_KEY`, `NGROK_AUTHTOKEN`, `NGROK_DOMAIN`에 이 노트북의 접근을 허용한다. [ngrok Domains](https://dashboard.ngrok.com/domains)에서 고정 도메인을 확인하고 [Your Authtoken](https://dashboard.ngrok.com/get-started/your-authtoken)의 값은 Secrets에 직접 등록한다. 일반 서버 시작과 추론에 `KAGGLE_API_TOKEN`은 필요 없다.
2. 노트북 맨 위 **Local Desk 서버 · 192K / MTP 3** 안내 다음의 첫 코드 셀을 실행한다. 서버 소스는 노트북 자체의 `_SERVER_SOURCE`에 보관되며, `restore_server_module()`이 `/kaggle/working` 디렉터리와 `kaggle_server.py`를 생성하고 SHA256으로 복원 내용을 검증한다. 같은 셀에서 해당 파일을 `ks` 모듈로 로드하지만 서버는 시작하지 않는다. 새 세션에서도 이 셀로 복원하므로 PC 파일이나 별도 데이터셋 업로드는 필요 없다. `.virtual_documents`는 편집기 분석용 임시 경로이며 서버 모듈의 보관·가져오기 경로로 사용하지 않는다.
3. 서버가 아직 실행 중이 아닐 때 그다음 시작 셀을 실행한다. 이 셀은 `/kaggle/working`을 가져오기 경로에 추가하고 모듈을 다시 불러온 뒤 아래 시작 함수를 호출한다. 처음에는 모델 다운로드·검증·빌드를 수행하고, 준비 완료 기록이 있으면 준비 단계를 생략한다. 파일 생성 셀만 실행하는 것으로는 서버·터널이 시작되지 않는다.

```python
import kaggle_server as ks

server, tunnel, api_url = ks.launch_service(allow_short_key=True)
```

4. PC에서 [start-kaggle.bat](start-kaggle.bat)를 실행한다. 새 주소가 발급됐다면 연결 창에 출력된 `API_URL`을 입력한다. 기존 앱의 API 설정에서 수동으로 주소와 키를 연결해도 된다. 키 값은 채팅이나 노트북 출력에 표시하지 않는다. 기존 프로필의 자동 요약 설정85% 시작/30% 목표는 이번 변경에서 유지했다.

노트북의 코드를 수정한 뒤에는 `Quick Save`로 실행 없이 버전을 보관한다. `.virtual_documents`나 작업 폴더 파일의 존재만으로 다음 세션 복원이 보장되지는 않는다. 이 PC의 [kaggle_server.py](kaggle_server.py)는 관리용 원본으로 유지하며, 이후 PC에서 수정해도 노트북에 자동 동기화되지 않는다. 노트북 아래의 과거 구축·진단 기록은 일반 시작에 실행하지 않는다.

서버가 이미 실행 중이면 시작 셀을 다시 실행하지 않는다. 다음 셀은 기록된 ngrok 고정 주소를 확인하며 현재 연결 상태까지 보장하지는 않는다. 고정 터널 기록이 없는 이전 세션에서는 localhost.run 로그를 읽는 호환 동작이 남아 있다.

```python
api_url = ks.tunnel_url()
print(api_url)
```

터널이 종료된 뒤에도 고정 주소 기록은 남는다. 현재 시작 셀의 `server.poll()`이 `None`이고 `tunnel.poll()`은 종료 코드이며 다른 ngrok 에이전트가 실행 중이지 않을 때만 `tunnel = ks.start_tunnel(server, allow_short_key=True)`로 같은 고정 주소에 다시 연결한다. `None`은 프로세스 실행 중을 뜻하며, 서버도 종료됐다면 이 터널 복구 절차를 사용하지 않는다. 이미 연결된 ngrok을 불필요하게 재시작하지 않는다.

실행 도구는 [kaggle_server.py](kaggle_server.py), 안전한 PC 키 전달·프로필 등록은 [kaggle_link.py](kaggle_link.py)다. `launch_service()`는 고정 터널 설정 확인, 준비, 서버 시작, 인증 검사, 터널 시작을 묶고 `(server, tunnel, api_url)`을 반환한다. 시작 실패 시 자신이 새로 시작한 프로세스를 정리하며 실행 중인 기존 서버를 교체하지 않는다. `start_tunnel()`만 따로 호출하다 실패한 경우에는 기존 모델 서버를 종료하지 않는다. 준비된 자산이 손상되거나 일부 없으면 자동 복구를 보장하지 않는다.

사용이 끝나면 Kaggle의 **Stop Session**으로 세션을 직접 종료한다. 서버·터널만 종료하려면 이 시작 셀이 반환한 프로세스에 한해 `tunnel.terminate(); tunnel.wait(timeout=15)`와 `server.terminate(); server.wait(timeout=15)`를 사용한다. **사용자 요청에 따라 별도 유휴 자동 종료는 구현하지 않았다.** Kaggle 자체의 유휴 정책과는 별개다.

모델·빌드·로그는 `/kaggle/temp/local-desk-qwen38`에 있어 저장 출력20GB 한도를 사용하지 않지만 세션 종료 후 사라질 수 있다. Kaggle 공식 안내의 GPU 세션 최대12시간, 계정 할당량·유휴 종료가 적용된다. 제한 회피나 자동 세션 재시작은 구현하지 않았다. 이전 localhost.run은 주소가 바뀌는 임시 HTTPS 중계여서 ngrok 계정 고정 주소로 전환했다. 계정이나 도메인을 변경하는 경우에는 API 프로필 URL과 해당 주소의 키 연결도 갱신해야 한다. Quick Tunnel의 SSE 미지원 때문에 Cloudflare 임시 터널은 사용하지 않았다.

Kaggle 약관의 개인·비상업적 사용 범위에서만 이용하며 상업용 제공자나 상시 호스팅으로 간주하지 않는다. 기존 설정 백업은 `data/settings.before-kaggle.json`에 보관한다. 노트북의 과거 실패 출력과 진단 셀은 초기 구축 기록이며, 완료된 다운로드·시험을 확인 목적으로 반복 실행하지 않는다.

### CPU와 RAM 관측

2026-09-26 실행 중인192K 서버를 변경 없이 관측했다. 생성 중 메인 스레드가 코어 하나 기준100%(4개 가상 코어 전체 기준25%)를 사용했으나, 이후 요청0인 유휴 상태의3초 표본에서는0%였다. 본체64개 언어층·출력층·KV와 MTP는 GPU에 배치돼 있었다. b11000 소스에는 CPU 샘플링과 CUDA 완료 대기 경로가 있고, 문법 제약은 GPU 백엔드 샘플링과 호환되지 않는다. 다만 실행 중 함수 스택은 수집하지 못했으므로 샘플링과 대기의 실제 기여도를 확정하지 않았다.

저장된 사용자 작업의 생성 속도는12.48~17.34 t/s였지만 입력·출력·캐시 조건이 달라 CPU 사용률 때문에 느려졌다는 대조 근거는 아니다. CPU 계산이 직렬 경로의 병목이면 t/s를 낮출 수 있고, GPU 완료를 기다리는 반복 확인이라면 높은 CPU 사용률 자체가 속도 저하를 뜻하지 않는다. 네이티브 프로파일러는 환경에서 발견되지 않았으며 새 도구 설치, 추론 추가, 서버 재시작, 스레드·대기 옵션 변경은 하지 않았다.

RAM 표본은 컨테이너 총사용28.559GiB/한도30GiB, 익명 메모리3.756GiB, 파일 캐시24.608GiB였다. 총사용에서 비활성 파일 캐시6.207GiB를 빼면22.352GiB로 사용자에게 보인 약22.4GiB와 거의 같다. 이는 파일 캐시 일부를 포함한 작업 집합 지표와 부합하지만 Kaggle 표시 공식 자체를 확인한 것은 아니다. 실제 서버 RSS는약4.219GiB였고 `mincore` 조회에서 본체16.353GiB·초안1.276GiB·비전0.864GiB 파일이 모두 캐시에 있었다. 파일 내용을 재독하거나 캐시를 비우지 않았다. 프로세스 RSS와 파일 캐시는 겹칠 수 있으므로 합산하지 않는다.

관측 시 스왑과 컨테이너 OOM 기록은0이었다. 호스트 전체의 `MemAvailable`을 컨테이너 잔여 한도로 해석하면 안 되며, 캐시 회수 가능성이 모든 순간의 메모리 여유를 보장하지도 않는다. 누적 페이지 폴트에는 로딩·이전 실험이 포함되므로 현재 t/s 저하의 증거로 사용하지 않았다. 높은 표시만으로 CPU 오프로딩·누수·스왑을 단정하거나 캐시를 강제 삭제하지 않는다.

### 도구 응답 형식

`Only tool and arguments are accepted` 사례는 HTTP200 응답을 받은 뒤 최종 도구 검증에서 발생했다. 당시 요청의 `json_object`는 JSON 문법만 보장하고 도구별 필드를 제한하지 않았다. 응답 원문은 보존돼 있지 않아 실제 추가 필드의 이름은 확인하지 못했다.

이제 ngrok 무료 고정 주소와 이전 localhost.run 주소의 `qwen3.8-27b-ud-q4-k-xl` OpenAI 호환 API에서 구조화 출력이 켜져 있고 네이티브 도구 모드가 아닐 때, 로컬 모델과 동일한 `json_schema`를 전송한다. 현재 허용·로드된 도구만 포함하며 최상위 `tool`·`arguments`와 도구별 인자를 제한한다. 토큰 예산 추정에도 스키마를 반영한다. 다른 제공자·모델과 네이티브 도구 모드, 구조화 출력 끄기는 기존 동작을 유지한다.

잘못된 응답에서 필드를 임의로 삭제하거나 도구를 실행하지 않는다. 완료된 모델 응답의 호출 형식·인자 검증이 실패하면 `call_validation` 오류 로그에 실행하지 않았다는 사실과 수정 안내를 남기고, 같은 세션·같은 작업에서 다음 수정 응답을 받는다. 로컬과 외부 API에 모두 적용하며 대화 기록을 지우지 않는다. 수정 응답은 현재 작업의 단계 한도를 사용하고 추가 API 요청 비용이 들 수 있다. 사용자 취소와 통신 장애는 기존대로 중단한다.

외부 API의 `Incomplete or rejected API response; no tool executed` 오류도 작업을 즉시 끝내지 않는다. 완료 표시 누락·출력 한도·거부되거나 지원하지 않는 완료 상태를 `response_validation` 오류로 기록하고, 다음 모델 요청에 오류와 도구 미실행 사실을 전달한다. 부분 응답은 이어 붙이거나 실행하지 않으며 이전에 완료한 작업은 보존한다. 출력이 잘렸다면 더 짧은 완성 응답을, 거부·차단됐다면 제한을 존중하고 차단 사유를 설명하는 종료 응답을 요청한다. 기존 단계 한도와 Stop은 유지하고, HTTP 재시도와 별개로 새 요청 비용이 들 수 있다. 다른 명시적 API 오류·네트워크 실패까지 모두 자동 복구하는 변경은 아니다.

잘못된 호출을 그대로 다시 전송하거나 입력 동작을 재실행하는 방식이 아니다. 기존 반복 방지·단계 한도·권한 검증은 유지한다. 모의 모델의 오류 후 정상 종료, 반복 오류의 단계 한도, 통신 오류 중단을 검증했다. **PC의 Local Desk를 완전히 종료하고 배치로 다시 실행하면 적용된다. Kaggle 모델 서버 재시작은 필요 없다.**

### 긴 사고 응답

외부 API 스트림의 사고 텍스트가200,000자를 넘으면 요청을 중단하던 조건을 제거했다. 네 가지 API 형식에서250,001자의 사고 뒤 정상 답변을 받는 회귀 검사를 통과했다. 답변100,000자, 도구 인자30,000자, 함수 이름100자의 보호와 수동 취소·미완료 도구 호출 거부는 유지한다. 제공자의 토큰 한도, API 프로필의 요청 시간 제한, 별도로 설정한 사고 예산까지 제거하는 변경은 아니다. 앱을 완전히 재시작해야 반영된다.

## 사고 예산과 중단 키

2026-09-26: Qwen3.8 27B의 `low / medium / xhigh`와 독립적인 `reasoning_budget_tokens`를 추가했다. 상단 사고 강도 옆 시계 버튼에서 설정하며 기본값은2,048토큰, `-1`은 무제한, `0`은 즉시 답변 전환이다. 새 항목이 없는 기존 설정에도2,048이 적용되지만 저장된 사고 강도와 사고 켜짐 여부는 바꾸지 않는다. 사용 중인 xhigh를 그대로 유지할 수 있다.

예산은 사고 블록에 적용한다. llama.cpp의 사고 종료 태그 강제 생성 기능을 사용하므로 예산 소진으로 서버를 종료하거나 전체 응답을 자르지 않는다. 이후 답변·도구 JSON 생성을 계속하며 완성되지 않은 도구 호출은 여전히 실행하지 않는다. 자동 요약에도 같은 예산이 적용된다. 초 단위 시간 제한은 아니며 입력 처리·답변 생성 시간과 전체 문맥 용량은 별개다. 예산을 너무 작게 잡으면 답변 품질이 낮아질 수 있다. 다른 로컬 모델과 외부 API의 설정은 바꾸지 않는다.

ESC는 Local Desk 세션을 중단하지 않는다. 중지 버튼과 F8은 유지하며, 대화상자 닫기와 도구가 대상 앱에 보내는 Escape는 그대로다. 모르는 사실·최신 정보는 오래 추측하지 말고 허용된 검색·자료 조회를 먼저 사용하도록 공통 지침을 추가했다. 비활성 도구나 차단 화면을 우회하도록 지시하지 않는다.

앱 전체 재시작 후 적용되며 이후 예산 저장은 모델 재로드 없이 다음 요청부터 반영된다. 설정·전송·완료 및 취소 처리와 독립 Tk 설정창을 검사했다. 실제27B의 예산 소진 응답과 품질은 아직 실측하지 않았으며 기존 GPU 연구나 운영 설정 파일은 다시 실행·수정하지 않았다.

새 항목이 없는 기존 설정에는85/65가 적용된다. 기능 적용에는 앱 전체 재시작이 필요하고 이후 비율 저장은 모델 재로드 없이 다음 사용자 요청부터 적용된다. 운영 설정 파일은 이번 수정으로 덮어쓰지 않았다. 모의 모델과 실제 독립 설정 창으로 검증했으며 새 모델 추론이나 속도 재측정은 하지 않았다.

`tool_parallel`은 최대4개의 독립적인 `workspace_read`, `workspace_search`, `browser_read`, `browser_tabs`, `terminal_output`을 묶는다. 같은 브라우저 호출은 직렬 처리하며, 입력·파일 변경·셸 시작·공유 색인 갱신은 이 묶음에 포함하지 않는다. 모델 추론 자체를 병렬화하는 기능은 아니다. 적용하려면 앱을 완전히 재시작한다. 실제 사용자 창에100회 입력하거나 모델 선택 성능을 실험하지 않고 모의 실행으로 검증했다. 자세한 한도와 기록은 [도구 계약](TOOL-CONTRACT.md#반복과-병렬-실행)을 참고한다.

## 캡처와 채팅

### 캐시·압축·코드 검색

가이드는 요청 앞부분에, 변화하는 작업 상태는 뒷부분에 둔다. 로컬 요청은 `cache_prompt=true`이며 같은 세션의 불러온 도구 그룹도 유지한다. 응답 아래의 `입력 KV 재사용`은 서버의 `cached_tokens` 또는 `cache_n` 보고 값이고, 보고가 없으면 미확인으로 표시한다. RAM 문맥 캐시 옵션과 현재 서버 슬롯의 KV 재사용은 서로 다르다. 저장된 이전 세션에서 입력2,287토큰 중2,155토큰 재사용을 확인했으나, 새 가이드의 전체 적중률이나 속도는 새로 측정하지 않았다. 도구 그룹·권한·가이드 변경, 세션 전환, 요약 후에는 일부 재계산이 발생할 수 있다.

후속 가이드 정리에서는 검색 선택 기준을 하나로 묶고 허용된 도구의 절차만 전달하도록 했다. 실제27B의 단순 판단4사례가 통과했고, 동일 가이드의 후속3요청에서2,375토큰 재사용을 확인했다. 전체 입력은2,424~2,441토큰이었다. 도구를 실제 실행하는 검사가 아니며 일반 작업의 성공률·속도 개선으로 해석하지 않는다. [상세 결과와 한계](TOOL-CONTRACT.md#캐시와-문맥-압축)를 참고한다.

`대화 자동 압축`은 기본 켜짐이며 끌 수 있다. 사용 가능한 문맥 예산의85%를 기준으로 오래된 기록을 같은 선택 모델에 요약시켜 별도 보존한다. 현재 요청·최근6개 기록·진행 중 작업은 보호한다. 요청당 최대2회, 실패 후 반복하지 않으며 유효하고 문맥을 줄이는 요약만 적용한다. 원문은 지우지 않고, 원문 편집·삭제 시 관련 요약은 무효화한다. 옆의 요약 보기에서 내용을 확인한다. 여전히 공간이 부족하거나 요약이 실패하면 일부 기록은 기존처럼 제외될 수 있으며 원문 재조회가 가능하다. 외부 API에서는 추가 요약 요청 요금이 발생할 수 있다.

`도구 선택`에서 `workspace_code_search`와 `workspace_symbols`를 켜면 로컬 검색 기반 RAG를 사용할 수 있다. 코드 조각을 BM25·식별자 단어로 순위화하고 경로·행·해시·읽기 참조를 반환한다. Tree-sitter로 Python·JavaScript·TypeScript·C/C++·C#·Java·Go·Rust의 정의와 구문상 참조를 찾는다. 임베딩 의미 검색이나 언어 서버의 정확한 참조 해석은 아니므로 Copilot과 동일한 검색 품질을 보장하지 않는다. 색인은 로컬에 저장하고 `.gitignore`·보호 경로·링크·일반 빌드 폴더를 제외한다. 파일 변경·삭제를 재검사하며 결과를 반환하기 전에 해시를 확인한다. 로컬 색인 자체는 외부 전송하지 않지만 API 모드에서 선택된 검색 결과는 모델에 전달된다.

도구 호출에는 선택 항목 `arguments.commentary`로 확인된 사실·남은 불확실성·다음 행동을 짧게 덧붙일 수 있다. 이는 사용자에게 보이는 진행 설명이며 비공개 사고 과정을 출력하는 기능이 아니다. 별도 설명용 추론 요청은 추가하지 않는다.

도구 이력은 호출 ID로 연결한다. 같은 도구의 반복 실행, 백그라운드 결과, 셸 종료 알림도 원래 호출을 구분한다. 채팅에는 실제 실행 상태·핵심 결과·최근 상태 이력을 접어 표시한다. 모델에는 같은 ID와 인자·상태·사실 기반 요약·원문 조회 위치를 전달한다. `delivered`는 성공 판정이 아니며 파일 적용·셸 종료·목표 달성을 구분한다.

긴 내용은 앞뒤 미리보기와 결과 개수를 제공하고 원문은 보존한다. `session_record`로 현재 세션의 특정 기록을 문자 단위 페이지로 다시 읽을 수 있으므로 원문 복구를 위해 도구를 재실행할 필요가 없다. 확실히 연결할 수 없는 예전 기록은 추측하지 않는다. 상세 형식과 한계는 [호출과 결과 이력](TOOL-CONTRACT.md#호출과-결과-이력)에 있다.

연구 자료는 `G:\LocalDesk-research-archive\notebook`으로 이전했고 기존 F 경로는 연결로 유지한다. 약23.14GiB의 동일 자료를 통합했으며 고유 실험은 삭제하지 않았다. 실제 경로·목록·수정 및 복구 주의사항은 [연구 보관 안내](RESEARCH-ARCHIVE.md)에 있다.

최신 도구 캡처는 **새 캡처가 성공할 때까지 같은 세션의 모델 입력에 유지**한다. 일반 도구 호출·오류·다음 대화로 없어지지 않는다. 원본 캡처는 기록에 남고, 재시작 후 최신 사진 한 장만 복원한다. 화면·브라우저 권한 해제나 파일 소실 때는 재첨부하지 않는다. 촬영 후 화면이 바뀔 수 있으므로 캡처를 실시간 화면으로 간주하지 않는다. 외부 API에는 보존 캡처가 다시 전송될 수 있고 요금과 입력 시간이 늘 수 있다. 아래 일회성 이미지 설명은 이전 정책이다.

입력창은 여러 줄과 실행 취소 `Ctrl+Z`, 다시 실행 `Ctrl+Y`를 지원한다. Enter는 전송, Shift+Enter는 줄바꿈이다. 사용자·모델 메시지의 복사 아이콘이나 메뉴로 전체 원문을 복사할 수 있다. 한글 글꼴 크기를 고정한 텍스트 위젯으로 교체했지만 실제 사용자의 IME 조합 상태에서 크기 튐이 사라졌는지는 추가 확인이 필요하다.

사고 스트림은 변경분을 붙이고 하단 여백을 둔다. 화면 끝에서는 끝을 유지하고, 위를 읽거나 드래그 선택 중이면 읽는 위치를 유지한다. 긴 텍스트는 표시량과 한 줄 길이를 제한하며, 저장 원문은 바꾸지 않는다. 도구 실행은 채팅 안의 접이식 상태 항목으로 표시한다. 긴 도구·사고 원문은 페이지 조회와 전체 복사를 제공한다. 검색은 Google을 먼저 사용하고 차단·접속 실패 시 Bing으로 전환하며 CAPTCHA나 로그인 우회는 하지 않는다. 검색·사고 렉의 유일한 원인이 확인된 것은 아니며 네트워크와 모델 자체 지연은 별개다.

사고 내용은 모델이 실제 반환한 텍스트만 별도 보존하고 다음 모델 입력에 자동으로 넣지 않는다. Copilot 내부 정책을 복제한 것은 아니다. 파일 편집·PowerShell 도구는 후속 승인으로 구현했으며 사용자가 목록에서 켠 뒤 사용할 수 있다. [도구 계약](TOOL-CONTRACT.md)에 입력 형식·변경 차이·출력·중단 정책을 명시했다.

## KV 정밀도

`Local model settings`에서 KV 캐시를 `Preset default`, `4-bit (Q4_0)`, `8-bit (Q8_0)`, `16-bit (F16)` 중 선택하고 `Save and unload`로 저장한다. K와 V에 함께 적용하며 모델 가중치 양자화를 바꾸는 옵션은 아니다. 기본값은 기존 모델 프리셋이다. 명시 Q4/F16에서는 Q8 전용 동적 적재를 끄고 정적 배치를 사용한다. Q4의 품질 변화와 F16의 VRAM 증가·로딩 실패 가능성이 있어 확인 후 적용한다. 모든 모델·엔진에서 각 형식이 지원됨을 보장하지 않으며 미지원 시 자동 대체하지 않는다. 사용자 설정은 자동으로 바꾸지 않았다.

Windows용 채팅 작업 에이전트. 로컬 GGUF 모델 또는 외부 API를 선택할 수 있다. 게임 에이전트와 별도 프로그램이며, 로컬 모델별 실행 옵션과 이미지 토큰 프리셋을 적용한다. 앱을 열거나 세션을 선택하는 것만으로는 추론·캡처·입력을 실행하지 않는다. 입력창에서 메시지를 보내면 선택한 모델로 작업을 시작한다.

## 실행

**최신 Q2_K_XL 운영 기준(2026-09-22)은 `front_native_reserve`다.** 검증된 모델·Q8 프로젝터 경로,8K 문맥, 이미지1024/1024토큰, RAM 문맥 캐시 꺼짐에서 [전용 운영 묶음](data/runtimes/llama-b11000-front-reserve/deployment.json)의 서버를 자동 선택한다. 텍스트에서는 FFN51+전체52~54를 RTX로 옮기고 이미지에서는 최신 상태·기준 배치·계산 예약을 복원한다. 다른 문맥 크기·RAM 문맥 캐시 켜짐은 이전 TPB16 정적 배치와 사용자 실행기를 유지한다. IQ2_S 등 다른 모델과 저장 설정은 바꾸지 않는다. **앱을 완전히 종료하고 다시 실행한 뒤 새 서버를 로드해야 한다.** 아래9월21일 기준 설명과 정적 배치 표는 이전 경로의 기록이다.

새 기준은 기존14응답을 재사용해 예열 제외 전체116.453초·텍스트49.345초·이미지67.108초다. 운영 서버의 로드와 DLL·메모리 감시는 무응답 검사로 확인했고 성능 시험은 반복하지 않았다. [현재 기준](data/research-baseline.json), [이전 기준 원본](data/baselines/medium_br8_iq3s_tpb16.json), [운영 적용 기록](PLACEMENT-STUDY.md#새-기준-등록과-운영-적용)을 참고한다. 검증된 모델 경로·크기·수정 시각 또는 런타임/계산표 해시가 다르면 새 경로를 거부한다. 전용 서버 선택은 저장 실행기 항목을 수정하지 않는다.

새 경로는 RTX 전용7850MiB·공유184MiB·가용 RAM4GiB를 감시하며 필수 계측 누락·초과 시 해당 앱의 서버만 중단한다. 9월23일 후속 요청으로600초 응답 종료와 다음 요청 차단을 제거했다. 다른 로컬 경로도 응답·HTTP 읽기 시간으로 종료하지 않으며 작업 전체 시간 제한도 없다. 로딩120초·메모리 보호와 외부 API 프로필 설정은 유지한다. 재부팅 후 GPU 카운터 식별자가 달라지면 검증 갱신 전까지 차단될 수 있다. 감시에 필요한 `numpy`, `psutil`은 [requirements.txt](requirements.txt)에 명시돼 있다. 긴 문맥·동시 그래픽 작업·장시간 안정성을 보장하는 결과는 아니다.

원클릭 실행: [start.bat](start.bat)을 더블클릭한다. 프로젝트 환경의 `pythonw.exe`를 별도 프로세스로 시작한 뒤 런처가 종료하므로 CMD 창은 앱 종료까지 남아 있지 않는다. 시작할 때 콘솔이 잠깐 보일 수 있다. 실행한 폴더와 관계없이 프로젝트 루트를 작업 폴더로 사용한다. Python 환경 누락 등 런처 실패 시에만 오류 창을 유지한다. 앱 실행 후 오류는 `data/launcher/<시각>-<실행ID>.stderr.log`에, 일반 출력은 같은 이름의 `.stdout.log`에 남는다. 앱 창이 뜨지 않으면 최신 오류 로그를 확인하거나 아래 PowerShell 직접 실행으로 진단한다. 로그는 자동 삭제하지 않는다. 실행 정책 우회는 해당 PowerShell 프로세스에만 적용되며 시스템 정책이나 관리자 권한을 변경하지 않는다. 앱을 여러 번 실행하면 별도 창이 생기므로 이미 열린 창을 먼저 확인한다.

PowerShell 직접 실행은 진단을 위해 기존처럼 콘솔에서 앱 종료를 기다린다. `-Detached`를 지정하면 배치파일과 동일하게 분리 실행한다. 이미 사용 중인 CMD에서 배치파일을 호출하면 그 CMD를 강제로 닫지 않고 프롬프트로 돌아온다. 워크스페이스 루트에서:

```powershell
.\desktop_agent\start.ps1
```

기존 Python은 `workspace/sd-scripts/venv_5050/Scripts/python.exe`를 사용한다. Pillow/requests/Playwright, 관리형 Chromium, markdown-it-py, OpenCV, tkinterdnd2, pypdf, httpx/httpx-sse, tiktoken, google-auth를 사용한다. 다른 환경에서는 [requirements.txt](requirements.txt)를 설치한 후 `python -m playwright install chromium`을 실행한다. 런처에 `-PythonPath`를 지정할 수 있다. 앱 자체는 Tkinter 네이티브 창이며 웹 서버가 필요하지 않다.

초기 기본 모델은 `G:/models/Qwen3.8-27B-GGUF`의 IQ2_S 및 Q8 비전 파일, 실행기는 `F:/llama/llama-server.exe`다. 기존 게임 모델 서버와 동시에 실행하면 VRAM이 부족할 수 있다.

Local Desk의 로컬 모델은 일반 로딩 `--load-mode none`을 기본 사용한다. 큰 GGUF 파일 매핑을 유지하지 않는 방식이며 GPU 사용을 끄는 옵션이 아니다. **기본 IQ2_S + Q8 비전은 RX580에 FFN55..63의9개 블록과 출력층을 배치한다.** 비전·attention/SSM·KV 및 나머지 주요 층은 RTX5050, 임베딩은 CPU에 둔다. 생성12/입력12스레드, batch512/microbatch128, Q8 KV, 체크포인트 유지다. **사용자 요청으로 IQ2_S와 Q2_K_XL의 Q8 이중 GPU 프리셋 모두 `CUDA_SCALE_LAUNCH_QUEUES=4x`, `-ub 128`을 기본 적용한다.** Q2_K_XL은 아래의55번 attention 공동 배치·호스트 가시 VRAM 우선 경로 OFF와 생성12/입력6스레드를 사용한다. 환경 변수는 해당 자식 모델 서버에만 설정하고 앱/시스템 환경은 바꾸지 않는다. 컨텍스트·사고 수준·이미지 크기 선택·현재 모델 파일은 바꾸지 않는다. 외부 API와 게임 에이전트, IQ2_XXS 및 IQ2_S의 기존 F16 프로젝터 배치는 변경하지 않는다. 변경 전 앱이 실행 중이면 완전히 종료한 뒤 다시 실행해야 한다. Q2_K_XL 이중 GPU 프리셋도 기존처럼 선택할 수 있다. 아래 연구 수치는 각 실험 당시 설정으로 측정한 기록이다.

운영 프리셋 경로의 실제 IQ2_S 서버에서 합성 계산·이미지 응답과 두 GPU 사용을 확인했다. 2026-09-21 사용자 승인으로 **Q2_K_XL의 정식 연구·운영 기준은 기존55번 공동 배치 + GCN 중간 타일 + 어텐션 내부 타일8 + IQ3_S 읽기 분담16 + MTP OFF**다. RX580에는 전체 블록52..54와56..63의11개·별도 FFN51/55·출력층을 둔다. CPU 임베딩·RTX 비전 및 나머지 블록을 유지한다. `--device CUDA0,Vulkan0,CUDA0,Vulkan0 --tensor-split 52,3,1,10`과 FFN55·post-attention 정규화의RX override는그대로다. Q8 KV·ub128/b512·큐4x·Vulkan 그래픽 큐·호스트 가시 VRAM 우선 경로 OFF·스레드를 유지하고 `--spec-type none`을 명시한다. **읽기 분담16은 CPU스레드16이나microbatch16이 아니며 ub는128 그대로다.** IQ2_S와 저장된 모델 선택·컨텍스트·캐시 설정은 변경하지 않고 CPU 반복 대기 OFF도 추가하지 않는다. **앱을 완전히 종료하고 다시 실행한 뒤 새 모델 서버를 로드해야 적용된다.** 검증된 동일 DLL과 기존14응답(예열 제외120.157초·이미지66.657초)을 재사용했으며 등록을 위한 모델 추론·기준선 재측정은 하지 않았다. [현재 기준점 등록](data/research-baseline.json), [이전 타일8 기준점](data/baselines/medium_mtp_off_fa_br8.json), [운영 적용·후속 검사](PLACEMENT-STUDY.md#읽기-분담16-운영-적용과-출력층-후속-검사)에 해시·검증 범위를 기록했다. 실제 그래픽 동시 부하·수시간 안정성·선택형2GiB 캐시 조합은 미검증이다.

이전 혼합8 연구에서 microbatch64/128/256 대조64응답과12K 같은 서버8라운드100응답을 검사했다. **당시에는 혼합8의 microbatch128을 유지했다.** 256은 동일 조건에서도 느렸고64의 짧은 이미지 시간에는 출력·캐시 차이가 섞였다. 약19분 지속 실행에서는 매 라운드마다 큰 RAM 증가가 누적되는 패턴이 없었지만, 새55번 배치나 수시간 안정성 보장은 아니다. 근거와 논문·공식 문서 검토는 [혼합8 적용 후 연구](PLACEMENT-STUDY.md#혼합8-적용과-후속-최적화-연구)에 있다.

### 로컬 모델 프리셋

후속12K/xhigh 연구에서는 응답을 이미지 인코딩·이미지/텍스트 prefill·reasoning/답변 생성으로 나누고, GPU별 VRAM·사용률 평균/p95/피크 빈도·CPU·상주 RAM·전용 커밋을 함께 비교했다. 전체 블록8개 RX 배치는비슷한 이미지 시간에 CPU7.71→4.86%, RTX 전용 메모리약222MiB 절감이 있었지만 RX 평균 사용률41.82→60.47% 및 고사용 지속 시간이 늘었다. 모든 자원을 함께 줄이는 승자는 없어 **운영 기본값은 유지했다.** 옵션·FFN 위치·전체 블록·안전 중단 및 측정 한계는 [연구 보고서](PLACEMENT-STUDY.md#iq2_s-응답-단계-및-자원-효율-비교)에 정리했다.

`CUDA_SCALE_LAUNCH_QUEUES`도 연구 자식 서버에만 미설정/0.25x/0.5x/2x/4x를 적용해42응답을 비교했다.4x의약1% 속도 이득에 RAM·공유 GPU 메모리 증가가 있었고 GPU 피크도 일관되게 줄지 않아 연구 당시에는 미설정을 유지했다. 이후 조합 비교와 사용자 요청에 따라 현재는 두 Q8 프리셋에4x+ub128을 적용한다. [큐 크기 연구](PLACEMENT-STUDY.md#cuda-작업-큐-크기-비교)와 [microbatch 조합 비교](PLACEMENT-STUDY.md#cuda-4x와-microbatch-조합)에 결과와 재현 명령을 기록했다. 이 조합의 성능 실측은 IQ2_S 기준이며 Q2_K_XL의 같은 폭 개선이나 장시간 안정성을 보장하지 않는다.

설정 톱니바퀴의 `Local model settings`에서 `Model preset`을 선택한다. 모델·짝이 맞는 프로젝터·기본 컨텍스트가 함께 채워지고 `Model options`에 모델별 옵션과 이미지 토큰이 표시된다. `Save and unload`로 저장하면 로컬 모드로 전환하고 기존 서버를 내려 다음 요청에서 새 설정으로 로드한다. 선택만 하거나 `Cancel`로 닫으면 현재 설정은 바뀌지 않는다.

`RAM prompt cache (2 GiB)`는 로컬 서버의 선택형 문맥 캐시다. **기본값은 꺼짐**이며 기존 설정 파일도 꺼짐으로 읽는다. 체크하면 미리보기에 `--cache-ram 2048`, 해제하면 `--cache-ram 0`이 표시된다. `Save and unload`로 저장한 뒤 새 서버부터 적용하며 프리셋 선택으로 이 체크 상태를 초기화하지 않는다. 외부 API에는 전달하지 않는다. 업데이트 전 앱은 완전히 종료하고 다시 실행해야 새 체크박스가 보인다.

긴 문서 두 개를 번갈아 재방문한 합성 연구에서 재방문·수정 시간을 약74% 줄였지만 처음 읽는 문서나 일반 텍스트·이미지 작업의 가속은 확인하지 못했다. 해당 실험의 추가 상주 RAM은 평균 약1.2GiB, 피크 약1.7GiB였다. **2GiB는 캐시 용량이지 프로세스 전체 RAM 상한이 아니다.** 이전 문맥 상태가 서버 RAM에 남을 수 있으므로 민감한 문서 작업 후에는 모델을 내려 캐시도 해제한다. 최초 활성화 시 RAM 사용과 보관 기간을 확인하며, 확인 거절·취소는 설정을 변경하지 않는다. 실측 근거와 한계는 [입력 캐시 연구](PLACEMENT-STUDY.md#입력-캐시와-재계산-연구)에 있다. 선택형 옵션만 추가했으며 저장된 사용자 설정은 자동 변경하지 않았다.

현재 **혼합8과의 조합도8K·12K에서 확인**했다. 문서 재방문·수정6건은 약168→44초, 추가 상주 RAM은 평균 약1.20GiB·피크 약1.72GiB였다. 전체132응답이 정답이었으나 일반 텍스트·이미지 작업의 속도 개선은 없었다. 긴 두 문서를 자주 오갈 때 켜는 선택지이며 기본값은 그대로 꺼짐이다. 이미지 문맥의 저장·복원이나3개 이상 문서에서도 같은 효과를 보장하지 않는다. [혼합8 캐시 조합 연구](PLACEMENT-STUDY.md#혼합8과-선택형-ram-캐시-조합)에 조건과 비용을 기록했다.

기존 모델 카탈로그의 다른 Qwen·UI-Venus NVFP4·Gemma 프리셋도 선택할 수 있다. 현재 모델 폴더, 실행기 옆 `models`, 초기 기본 모델 폴더에서 파일 쌍을 찾으며 없으면 폴더를 직접 고른다. 자동 다운로드는 하지 않는다. 경로를 직접 입력해도 알려진 모델 파일명에 따라 전용 옵션과 이미지 토큰을 적용하고 잘못된 프로젝터 조합은 거부한다. 알려지지 않은 모델은 일반 실행 옵션과 이미지1024/1024를 사용하므로 호환성 확인이 필요하다.

Q2_K_XL 프리셋은 Local Desk 전용이며 b11000 CUDA 실행기와 [검증된 TPB16 조합 DLL](data/runtimes/llama-b11000-vulkan-gcn-br8-tpb16/ggml-vulkan.dll)을 사용한다. 이 PC에서 확인한 `CUDA0=RTX5050`, `Vulkan0=RX580` 장치 이름을 전제로 한다. 해당 모델을 시작할 때 자식 서버의 `GGML_BACKEND_PATH`·`GGML_VK_GCN_MEDIUM_TILE=1`·`GGML_VK_GCN_FA_BR8=1`·`GGML_VK_GCN_IQ3_TPB16=1`·`GGML_VK_VISIBLE_DEVICES=0`·기존 큐/메모리 옵션을 설정하며 앱/시스템 환경은 바꾸지 않는다. DLL이 없으면 CPU나 다른 장치로 몰래 대체하지 않고 오류를 낸다. 행4·작은down타일·256스레드·직접Q8·마스크후보·프로파일러는차단한다. Q8 프로젝터만 허용하며 MTP는 켜지 않고 이미지 MTP 연구용 서버/core도 적용하지 않는다. 이전 구성의8K/12K 반복 검증을 새 조합의 장시간 안정성 검증으로 간주하지 않는다. 문맥 용량을 채운 긴 입력·실제 그래픽 동시 부하·다른실행기버전은보장하지않는다. 프리셋을 고른 뒤 `Save and unload`해야 선택이 저장되며, 기존Q2_K_XL 사용자는 앱 재시작과 새 서버 로드로 새 기준을 사용한다.

IQ2_S + Q8 비전은 [기존 공식 Vulkan DLL](data/runtimes/llama-b11000-vulkan/ggml-vulkan.dll)과 같은 장치 이름을 사용하며 이번 중간 타일 적용 대상이 아니다. 모델을 바꾸거나 프리셋을 다시 저장하지 않아도 해당 파일명을 선택한 기존 설정에 새 배치가 적용된다. DLL 누락은 시작 전에 명시적 오류로 알리며 CPU로 몰래 되돌리지 않는다. 부모 환경은 변경하지 않고 자식 서버에만 DLL 경로를 전달한다. 다른 GPU 프로그램과 동시에 실행하거나 컨텍스트를 키우면 메모리 여유가 달라질 수 있다.

프리셋 선택 경로로 Q2_K_XL 서버를 시작해 합성 계산과 이미지 숫자 읽기를 확인했다. [프리셋 적용 검증](data/benchmarks/q2xl-profile-smoke-20260919-141348/results.json)에 실행 인수와 부모 환경 변수 보존 결과를 기록했다.

컨텍스트는 사용자가 지정한 값을 유지하며 **프리셋을 명시적으로 선택할 때만** 해당 기본값으로 바꾼다. 추론 설정·작업 한도·API 프로필은 프리셋 선택으로 바꾸지 않는다. 창 제목과 로딩 상태는 실제 모델을 표시한다. 서버 재사용 조건에 모델·프로젝터·이미지 토큰·컨텍스트가 포함된다. Qwen3.8 27B의 사고 수준과 ON/OFF는 요청별로 적용하므로 서버를 재로드하지 않으며, 다른 모델의 사고 토큰 예산 변경은 기존처럼 재로드한다.

9B Distill-Heretic은 현재 환경에서16K·이미지192/384로 실제 로드(약4.7초)와 짧은 텍스트 생성을 확인했다. 모든 모델·하드웨어의 메모리 적합성이나 화면 인식 정확도를 보장하지 않으며,192/384 이미지는1024/1024보다 작은 글씨 정보가 줄어들 수 있다. GPU 전체 레이어 요청은 llama.cpp의 메모리 fit 결과까지 보장하는 의미가 아니다.

### IQ2_XXS GPU 배치

현재 IQ2_XXS + Q8 비전은 기존 FFN58..63의6개 블록을 CPU에 둔다. 두 블록을 추가로 GPU에 옮기는 실험 후 사용자 요청으로 원래 배치를 복원했다. IQ2_XXS 전용 GPU 추가 배치 재정의는 제거했으며 컨텍스트 크기에 관계없이 기본 프리셋 배치를 따른다. IQ2_XXS의 F16 프로젝터는 기존 FFN55..63을 유지하고 게임 에이전트 설정도 바꾸지 않는다. IQ2_S의 RX580 적용과는 별개이며 아래 비교의 현재 IQ2_XXS 적용값은58..63이다.

**기본 배치는 변경하지 않았다.** 임베딩397MiB(Q2_K)를 GPU에 두기 위해 FFN을 더 CPU로 옮긴 후보는 느려졌다. 이는 임베딩 단독 GPU 이동 효과가 아니라 제한된 VRAM 안에서 교환한 전체 배치의 결과다. FFN down 분리 후보의 전체 시간 차이는 약0.8%에 불과하고 메모리를 더 사용해, 측정2회만으로 기본값을 바꿀 근거가 부족하다. 출력층682MiB(Q4_K)은 기존 CPU_REPACK을 유지한다. 상세 로그로 임베딩 CPU/CUDA0 및 출력 CPU_REPACK 배치를 확인했다. 메모리 수치는 Windows 프로세스 GPU 카운터의 표본 최대이며 장시간 안정성·순간 최고치·추론 정확도에 대한 검증은 아니다. [비교 원자료](data/benchmarks/iq2s-placement-20260919-073556/results.json), [메모리 요약](data/benchmarks/iq2s-placement-20260919-073556/summary.json)과 같은 폴더의 상세 로그를 참고한다.

추가 세분화 연구는 [PLACEMENT-STUDY.md](PLACEMENT-STUDY.md)에 정리했다. 25개 배치·스레드 후보를 비교했으며 현재 기본 텐서 배치와 스레드 설정은 변경하지 않았다.

후속 RX580 2048SP 8GB 연구도 같은 보고서에 추가했다. CUDA RTX5050 + Vulkan RX580 혼합 실행에서 CPU FFN55..63과 출력을 RX580으로 옮기면 캐시 재사용 텍스트 시간이 약43~45% 줄었다. 반면 긴 새 입력의 첫 이미지 응답은 약64% 느려졌고 새 숫자 이미지 검사도 느려, 화면 작업 전체의 개선으로 해석할 수 없다. 출력층만 이동하는 후보는 양쪽에서 작은 이득이 있었다. 합성 응답150개와 간단한 정확성 검사 결과를 보존했으며 운영 설정은 자동 변경하지 않았다.

비전 타워 교환 후속 실험에서는 비전 인코딩 구간이 RTX 약0.78초에서 RX 약10.8초로 늘었다. 확보한 RTX 메모리에 출력·FFN·임베딩을 되돌려도 이미지 처리 손해를 상쇄하지 못해 비전은 RTX 유지가 권고다. CPU FFN·출력을 RX로 옮기면 서버 CPU 피크는 약85%에서9% 미만으로 줄었지만 RAM 작업 집합 표본 최대는 약9.46GiB로 유지됐다. 이는12논리프로세서 기준1초 CPU 시간 차분이며 전체 PC 순간 피크가 아니다. 응답65개 및 CPU·RAM·GPU 원자료를 같은 연구 보고서에 추가했다.

FFN9+출력 배치의 정밀 RAM/CPU 후속 연구에서는 상주 RAM 약9.29GiB 중 GGUF 매핑이약7.40GiB로 확인됐다. 연구 실행만 `--load-mode none`으로 바꾸면8K 마지막 작업 집합1.61GiB,12K1.83GiB로 줄었고 응답 시간은 비슷했다. 전용 커밋은약13GiB로 남으므로 물리 RAM과 구분해야 한다. CPU는추론 중약8%, 유휴거의0%였으며 Vulkan 실행 주소의 PAUSE 반복문을 확인해GPU 완료 능동 대기가 포함됨을 입증했다. 체크포인트를 끄면 메모리 절감은 작고 재계산으로 느려졌다. 운영 설정은 변경하지 않았으며 자세한 방법·원자료·한계는 같은 보고서의정밀 분석 절에 있다. 계측 도구는 [benchmark_resources.py](benchmark_resources.py)다.

### Q2_K_XL 비교 연구

같은 리비전의 UD-Q2_K_XL을 다운로드하고 크기·SHA256을 검증했다. 일반 로딩·비전RTX를 유지하며 FFN45..63의19개+출력층을 RX580에 둔 후보를 IQ2_S의 FFN9개 배치와 비교했다. 반복 이미지11.41→17.21초, 텍스트3.88→5.25초로 느려졌지만, 작은20개 합성 품질 과제는 사고OFF에서17→19개, low에서18→20개 통과했다. 이는 실제 다단계 작업 성공률이 아니며, low의 일부 이미지 요청은36~53초가 걸렸다. 상주 RAM은 둘 다 약1.6GiB였고 Q2의 전용 커밋·RX 메모리는 증가했다. **후속 요청으로 Q2_K_XL 프리셋만 추가했으며 기본 모델은 IQ2_S로 유지했다.** 이제 Q2_K_XL 프리셋을 선택하거나 알려진 모델 파일명을 지정하면 검증한 이중 GPU 옵션을 사용한다. [연구 보고서](PLACEMENT-STUDY.md)에 원자료·재현 명령·실패 후보의 CUDA 오류를 기록했다.

## 외부 API

상단 구름 버튼의 `API settings`에서 `External API`를 선택한다. `Connection`에서 형식·URL·모델·Vertex·키 회전을, `Generation`에서 토큰·스트리밍·추론 옵션을 설정한다. 프리셋은 입력 편의용이며 계정의 모델 접근 권한까지 확인하는 것은 아니다. `Save`는 설정을 저장하고 기존 모델을 내린다. API 모드에서는 llama.cpp/GPU 모델을 로드하지 않는다. 로컬로 돌아갈 때는 같은 창에서 `Local llama.cpp`를 선택한다.

| format | 엔드포인트 예시 | 인증 |
|---|---|---|
| openai | `https://generativelanguage.googleapis.com/v1beta/openai/chat/completions` | Bearer API key |
| responses | `https://api.openai.com/v1/responses` | Bearer API key |
| gemini | `https://generativelanguage.googleapis.com/v1beta` | x-goog-api-key |
| anthropic | `https://api.anthropic.com/v1/messages` | x-api-key |

Gemini 기본 모델은 `gemini-3.8-flash`다. Google의 `/v1beta/chat/completions` 주소를 입력하면 공식 호환 경로인 `/v1beta/openai/chat/completions`로 보정한다. 다른 제공자에는 그 제공자가 지원하는 형식·주소·모델을 함께 지정한다. Responses 형식을 Google의 Chat Completions URL에 보내는 등 서로 다른 규격을 혼용할 수는 없다. Gemini native는 모델명으로 `generateContent`/`streamGenerateContent` 경로를 만든다.

NVIDIA 등 일반 OpenAI 호환 서버에서는 `vertex`를 끄고 해당 URL과 모델명을 사용한다. 예를 들어 `https://integrate.api.nvidia.com/v1/chat/completions`에는 Google 전용 `extra_body.google.thinking_config`를 보내지 않는다. Gemini/Vertex 설정에서 남은 `thinking_budget=0`이나 `include_thoughts=true`도 NVIDIA 요청에는 넣지 않는다. 비Google OpenAI 설정에서는 이 Google 전용 입력란이 비활성화되고 저장 시 정리되며, 별도로 저장한 Vertex 프로필은 바꾸지 않는다.

HTTP400/422 응답에 알려진 옵션 이름이 있으면 `server referenced: response_format`처럼 필드 이름만 표시한다. 서버 오류 원문이나 반사된 대화·키는 출력하지 않는다. `response_format`이 지적되면 해당 모델의 JSON mode 지원 여부를 확인하고 `structured_output`을 끈 상태로 비교할 수 있다. `max_tokens`가 지적되면 `max_output_tokens`와 `token_limit_field`를 확인한다. 모든 호환 API가 같은 선택 옵션을 지원한다고 가정하지 않으며, 400 오류에서 옵션을 몰래 바꿔 자동 재전송하지 않는다.

일부 호환 모델은 JSON mode를 요청해도 인사말처럼 일반 문장으로 답한다. API 응답이 정상 종료됐다면 이런 문장은 **도구 없는 최종 채팅 답변**으로 표시한다. 문장 속 코드나 JSON 예시를 추출해 실행하지 않는다. 응답 전체가 하나의 JSON 코드 블록인 경우에는 코드 울타리만 제거하고 기존 액션 검증을 적용한다. 손상된 JSON·여러 JSON 객체·잘린 출력·미완료 응답은 계속 거부한다. 일반 답변을 표시하는 것과 모델이 도구 호출 형식을 따르는 것은 별개이며, 도구를 쓰려면 유효한 액션을 생성해야 한다.

파싱 실패 시 전송 데이터(`API SSE event`/`HTTP response`)의 JSON 오류, 빈 답변, 모델의 잘못된 액션 JSON을 구분해 알린다. 오류 메시지에는 응답 원문을 넣지 않는다. 답변 메타데이터의 `reply_format`은 `action_json`, `fenced_json`, `plain_text`, `native_tool`로 기록한다.

`Generation`의 `native_tools`는 OpenAI 호환 Chat Completions에서만 선택할 수 있으며 기본은 꺼짐이다. 켜면 로드된 도구만 `tools`에 넣고 한 번에 하나의 네이티브 함수 호출을 요청한다. `structured_output` 대신 도구 규격을 사용하며 스트리밍·일반 응답 모두 종료 후 인수를 검증한다. 과거 호출과 그 결과는 대응하는 `assistant.tool_calls` / `tool` 역할로 변환한다. 다른 API 형식과 로컬 모델은 축약 JSON 방식을 사용한다. 제공자가 네이티브 도구 호출을 지원해야 하며 실패 시 JSON 방식으로 몰래 바꿔 재전송하지 않는다. 네이티브 경로는 모의 서버로 검증했고 이번 변경에서 유료 제공자에 실제 요청하지 않았다.

### API 프로필

API 설정 창 상단의 `API profile`에서 이름별 설정을 저장하고 불러온다. 최대30개, 이름은1~80자이며 기존 단일 설정은 이름 없는 현재 설정으로 그대로 유지된다.

- `+`: 현재 연결·모델·생성·재요청 설정을 새 이름으로 저장한다. `↓`: 불러온 프로필을 현재 편집값으로 덮어쓴다. 같은 이름이 있으면 확인한다. 이름을 바꾼 사본도 `+`로 만들 수 있다.
- 프로필 목록에서 선택하면 편집 창에 불러온다. 저장하지 않은 변경이 있으면 버릴지 묻는다. **불러오기나 프로필 저장만으로 현재 실행 설정을 바꾸거나 요청을 보내지는 않는다.** 아래 `Save`를 눌러 해당 설정을 활성화한다. 선택한 프로필의 수정값도 함께 저장된다.
- `×`: 확인 후 선택한 저장 프로필만 삭제한다. 대화·세션은 삭제하지 않는다. 현재 활성 설정의 사본은 유지하므로 활성 프로필을 삭제해도 사용 중인 설정이 갑자기 다른 모델로 바뀌지 않는다.
- 프로필 사본을 만들 때 일반 API 키 목록도 별도 암호화 영역으로 복사한다. 같은 서버 주소의 프로필끼리도 이후 키 추가·삭제가 섞이지 않는다. 키 관리 창에서 저장한 변경은 해당 키 목록에 즉시 반영되며, 연결 필드의 저장/취소와는 별개이다.
- Vertex 프로필 사본은 같은 암호화 JSON 키 참조를 공유할 수 있다. 한 프로필에서 키를 교체·제거하더라도 다른 프로필이나 활성 설정이 참조하는 키는 지우지 않는다. 어느 설정에서도 참조하지 않는 프로필 자격 증명만 정리한다. Google Cloud의 실제 키 폐기는 별도 작업이다.
- 프로필과 재요청 횟수는 설정 파일에 보존되며 앱을 다시 열어도 남는다. 설정 파일에 평문 API 키나 서비스 계정 개인 키를 넣지는 않는다.

### 키 관리

- 채팅이나 코드에 노출된 키는 폐기·재발급하고 앱의 `Manage API keys` 창에 입력한다. 실제 키는 코드·설정 JSON·세션 로그에 넣지 않는다. 이 작업 중 대화에 제시된 키도 저장하거나 실제 요청에 사용하지 않았다.
- 마스킹된 입력창에 키를 붙여넣고 `+`로 추가한다. 여러 키는 줄바꿈·쉼표·세미콜론으로 구분할 수 있다. 최대20개이며 목록에서 제거한 뒤 `Save encrypted keys`로 저장한다.
- `data/api-keys.dpapi`에 Windows DPAPI 사용자 범위로 암호화해 저장한다. 같은 Windows 사용자 계정에서 복호화한다. 서버 origin과 프로필 참조 ID로 키를 분리하므로 Google 키가 다른 호스트로 자동 전달되지 않는다. 기존 이름 없는 설정의 키 목록도 계속 지원한다. 세션 삭제는 공용 API 키 저장소를 삭제하지 않는다. 같은 사용자 권한으로 실행되는 악성 코드까지 막는 보안 경계는 아니다.
- `on_failure`: 정상 키를 유지하고 HTTP401/403/429에서 등록된 다음 키를 시도한다. `round_robin`: 성공한 요청마다 시작 키도 순환한다. 키 교체 역시 아래 `max_retries` 한도를 소비한다. HTTP401/403으로 거부된 키는 같은 요청에서 다시 선택하지 않는다. 같은 키로도 일시 오류 재시도를 할 수 있으며 부분 응답 이후에는 재시도하지 않는다.
- `Retry-After`를 존중하며 대기 시간이 요청 제한을 넘으면 중단한다. 키 회전은 프로젝트 단위 쿼터나 제공자 제한을 우회하는 기능이 아니다. URL에 키를 넣지 않으며 HTTPS를 사용한다. 로컬 테스트용 HTTP는 loopback만 허용하고 자동 리다이렉트는 따르지 않는다.

### 실패 재요청

`Generation` 탭의 `max_retries`는 **최초 요청 이후의 추가 시도 수**다. 기본2, 범위0~10이며0은 자동 재요청/실패 시 키 교체를 끈다. 예를 들어2이면 키 교체를 포함해 한 모델 응답당 최대3번 HTTP 요청을 보낸다. Vertex에도 동일하게 적용하고, 각 프로필에 별도로 저장한다.

- 재시도 대상: HTTP408/429/500/502/503/504/529, 응답 수신 시작 전의 연결 오류·연결/읽기 시간 초과·일부 전송 오류. HTTP401/403은 아직 거부되지 않은 다른 API 키가 있을 때만 한도 안에서 교체한다. Vertex 인증 실패는 무한히 반복하지 않는다.
- 재시도 제외: HTTP400/404 등의 설정 오류, 거부/불완전 응답, JSON·도구 검증 실패, HTTP200 응답을 받기 시작한 뒤의 스트림/전송 오류. 이미 받은 응답을 이어 붙이거나 도구를 다시 실행하지 않는다. `call_validation`·`response_validation` 복구는 같은 HTTP 요청의 재전송이 아니라 오류 이력이 추가된 다음 작업 단계이며 `max_retries=0`이어도 단계 한도 안에서 진행한다.
- 대기는 기본1·2·4·8초로 늘어나며 서버의 `Retry-After`가 있으면 그 값을 따른다. 전체 요청과 모든 재시도·대기는 하나의 `timeout_seconds` 제한을 공유한다. Stop으로 대기 중에도 취소할 수 있다.
- 진행 상태에 재시도 횟수를 표시하고, 성공 답변에는 실제 HTTP 시도 수를 남긴다. 네트워크 오류 전 서버가 이미 요청을 처리했다면 재시도에 추가 비용이 발생할 수 있다. 도구 중복 실행을 막는 것이 제공자의 중복 과금 방지를 보장하지는 않는다.

### 생성 설정

- `timeout_seconds`: 최소10초의 정수이며 입력 상한은 없다. 기존600초 상한을 제거해 `10800`(3시간)처럼 지정할 수 있다. 전체 요청과 재시도 대기에 적용하며 HTTP 읽기·쓰기 대기도 같은 값을 사용한다. 연결 수립 제한10초와 Stop 취소는 유지한다. 앱을 완전히 재시작한 뒤 `Generation`에서 원하는 값을 저장한다. 기존 프로필 값은 자동 변경하지 않으며 제공자·터널·Kaggle 세션 자체의 제한까지 없애지는 않는다.
- `stream`: SSE 스트리밍을 켜거나 끈다. 응답이 정상 종료되고 전체 JSON 액션을 검증한 뒤에만 도구를 실행한다. 토큰 한도에 잘린 출력, 거부 응답, 네트워크 중단은 실행하지 않는다. Stop은 응답 다음 조각을 기다리지 않고 클라이언트 요청을 취소한다. 이미 서버에서 처리한 요청의 과금까지 취소된다는 뜻은 아니다.
- `reasoning_effort`, `thinking_level`, `thinking_budget` 중 하나만 지정한다. `default` 또는 예산-1은 제공자의 기본값을 사용한다. OpenAI/Responses는 effort, Gemini native는 thinkingConfig, Google OpenAI 호환은 Google 확장 필드, Claude는 adaptive effort 또는 budget으로 변환한다. `include_thoughts`는 제공자가 공개하는 요약이 있을 때 표시한다. 모든 모델이 모든 옵션을 지원하는 것은 아니며 Gemini 3 계열처럼 추론 자체를 끌 수 없는 모델도 있다. API 모드에서는 상단 로컬 추론 토글 대신 이 설정을 사용한다.
- `max_output_tokens`는 제공자별 출력 상한이며 추론 토큰을 포함할 수 있다. 사고 예산보다 충분히 크게 잡는다. Kaggle Qwen OpenAI 프로필은 `-1`로 요청별 출력 토큰 상한을 해제할 수 있다. 서버의 `--n-predict -1`과 함께 사용하며 다른 제공자에서는 이 값을 거부한다. 무제한 모드에서도 문맥 구성용으로4,096토큰을 예약하지만 이는 생성 종료 조건이 아니다. 문맥 용량·요청 시간·응답 문자 수·도구 인자 크기 보호는 유지한다. 기존 프로필은 앱을 완전히 재시작한 뒤 이 값을 직접 `-1`로 저장한다. `token_limit_field`는 OpenAI 호환 서버가 요구하는 `max_tokens`/`max_completion_tokens`를 선택하며 auto는 모델 계열에 맞춰 기본값을 고른다.
- `structured_output`: OpenAI/Responses JSON mode, Gemini JSON MIME, Claude JSON schema 옵션을 사용한다. 제공자가 지원하지 않으면 끌 수 있지만 로컬 JSON/도구 검증은 항상 유지된다. 복잡한 스키마를 거부하는 서버에서도 승인·입력 제한이 완화되지는 않는다.
- `tokenizer`: o200k_base, cl100k_base, p50k_base, r50k_base 또는 estimate. 첫 tiktoken 사용에는 공개 인코딩 파일 다운로드가 필요할 수 있다. **Gemini/Claude의 공식 토크나이저와 같다고 보장하지 않으며 문맥 예산 추정용**이다. 상단도 API est.로 표시한다. 실제 사용량은 응답 usage를 기록하고, 서버 처리 속도가 없으면 입력/출력 속도는 미측정으로 둔다. 별도로 표시하는 요청 평균 출력은 네트워크·대기를 포함한 전체 경과 시간 기준 추정치다.
- API `context_tokens`는4096~2097152의 클라이언트 예산이다. 실제 모델의 컨텍스트를 확장하지 않는다. 출력·이미지·메시지 여유와 도구 스키마 비용을 제외해 문맥을 구성하고, 한도를 넘으면 오래된 이전 대화부터 전송에서 제외한다. API 토큰 수는 추정치이므로 실제 제공자의 계산과 다를 수 있다.

### Vertex

`vertex`를 켜고 **`Select JSON key file...`에서 Google Cloud 서비스 계정 JSON 키 파일을 선택**한 뒤 `Save`를 누른다. `project_id`를 자동으로 읽어 `Project (from JSON)`에 표시하므로 프로젝트 ID나 인증 토큰을 직접 입력할 필요가 없다. Vertex를 켜면 URL·API 키 회전 입력은 숨기고 JSON 키 선택 화면을 표시한다. JSON에 지역 정보는 없으므로 `Region (optional)`에서 필요할 때만 지역을 선택한다. 기존 기본값은 `us-central1`이며 비우면 `global`을 사용한다.

이는 모델에게 파일을 업로드하는 일반 첨부 기능이 아니라 **로컬 인증 파일 가져오기**다. 파일은 UTF-8 JSON, 최대64KB이며 `type: service_account`, 프로젝트·서비스 계정 이메일·개인 키·Google 토큰 엔드포인트를 검증한다. 일반 프로젝트 설정 JSON, 사용자 로그인 JSON, 손상된 키는 거부한다. 자격 증명을 담은 JSON을 대화창에 첨부하지 않는다.

선택한 파일은 설정 또는 프로필 저장 전까지 메모리에만 보관한다. 저장하지 않고 설정 창을 닫으면 보관하지 않는다. 저장하면 Windows DPAPI로 암호화해 `data/api-keys.dpapi`에 보관하고, 설정 JSON에는 비밀이 아닌 프로젝트 ID와 자격 증명 참조 ID만 넣는다. 원본 파일 내용이나 경로를 대화·첨부·로그에 저장하지 않는다. 원본 파일을 이동해도 저장된 암호화 복사본을 사용한다. 다른 JSON을 선택해 저장하면 해당 설정의 키를 교체하며, `−` 버튼 후 저장하면 해당 설정의 참조를 제거한다. 다른 프로필 또는 활성 설정에서 참조하는 키는 유지한다. Google Cloud에서 키 자체를 폐기하는 작업은 별도로 해야 한다.

Google 인증 라이브러리가 이 서비스 계정으로 OAuth 토큰을 발급·갱신해 Vertex 요청의 인증 헤더에 사용한다. 별도의 `gcloud auth application-default login`은 필요하지 않으며 ADC로 자동 대체하지 않는다. 이전 ADC 방식으로 저장한 설정은 JSON 파일을 한 번 선택해 다시 저장해야 한다. 인증 갱신 요청에는 별도 제한 시간이 있어 중단 시 정리가 잠시 지연될 수 있다.

Gemini native, OpenAI 호환 Chat Completions, Anthropic Claude 경로를 지원하며 Vertex Responses는 지원하지 않는다. 모델은 해당 프로젝트·지역에서 활성화되어 있어야 하고, 서비스 계정에 Vertex 사용 권한과 프로젝트의 API·결제 설정이 필요하다. JSON 파일이 유효하다는 사실만으로 실제 호출 권한까지 확인되는 것은 아니다.

### 전송과 검증 범위

API 대기 중 상태 표시에는 `image + text`/`text`, 인증·응답 헤더 대기·답변 수신·재시도 단계, 시도 수와 경과 시간을 표시한다. 캡처 파일이 저장됐다는 것과 API가 이미지를 처리해 답변했다는 것은 다르다. `No desktop window selected`는 대상 창 선택 문제이고, HTTP429는 제공자의 할당량/용량 제한이다. 두 오류를 이미지 전송 실패로 단정하지 않는다.

API 취소는 Stop 버튼·전역 F8/Esc·앱 종료·클라이언트 취소 등의 원인과 경과 시간·대기 단계를 표시한다. 취소된 응답에서는 도구를 실행하지 않지만 같은 작업의 이전 단계에서 실행한 입력까지 취소되는 것은 아니다. 실패 시 모델·호스트·형식·이미지 유무·HTTP 상태·시도 수·수신 문자 수·출력 한도를 `api_request` 메타데이터로 보존하며 키·프롬프트·원본 서버 오류 본문은 넣지 않는다. 400/422는 옵션·입력·토큰 한도를, 404는 경로·모델 ID·지역·접근 가능 여부를 확인한다. 서버 오류에서 알려진 필드와 이미지/문맥/모델 오류 범주만 추려 안내한다. 잘못된 모델 action JSON은 risk와 arguments 오류를 구분하며 도구를 실행하거나 자동 수정·재요청하지 않는다.

스트리밍 완료 이벤트를 받으면 서버가 연결을 계속 열어 두더라도 종료를 기다리지 않는다. OpenAI/Gemini는 뒤따르는 usage 정보를 최대0.2초 더 수집하며, 누락 시 사용량을 추정해서 채우지 않는다. 완료 이벤트 자체가 오지 않으면 설정한 전체 타임아웃을 적용하고 마지막 대기 단계를 오류에 표시한다. 429 재시도는 기존 한도·대기 정책을 유지한다. 이 동작은 열린 연결을 재현한 모의 스트림과 캡처→Vertex 형식 이미지 요청→최종 답변 흐름으로 검사했으며, 실제 계정의 쿼터나 서버 응답 지연까지 해결한다는 의미는 아니다.

API 모드에서는 대화, 호출·실패 로그, 파일 경로, 읽은 첨부 내용과 현재 캡처가 외부 서버로 전송될 수 있다. 세션/서버/모델이 바뀌면 첫 전송 전에 확인한다. 이미지의 다음 요청 한 번 사용 정책은 유지하지만 제공자의 보관 정책까지 통제하지는 못한다. Responses에는 `store: false`를 보낸다. 자격 증명은 프롬프트가 아니라 인증 헤더에만 사용한다.

네 형식의 요청/응답·스트리밍·이미지 변환, 키 회전, Vertex 서비스 계정 JSON 검증·암호화·토큰 갱신·인증 헤더, 취소와 리다이렉트 차단은 모의 서버/테스트 키로 검사했다. 설정 UI에서 JSON 선택·취소·프로젝트 자동 채우기·저장·재열기도 검사했다. 2026-09-18 사용자 승인 아래 고정 문장으로 프로필당1회 진단했을 때 Vertex Gemini는 약2초에 정상 finish, NVIDIA GLM은 약28초에 HTTP200 이후 risk/arguments 검증 실패, Muse는200초 동안 응답 헤더를 받지 못해 시간 초과였다. 이 진단은 실제 대화·이미지·도구 실행을 포함하지 않았으며 기존400/404를 재현하지 못했다. 모델의 일반 작업 성공률이나 향후 제공자 가용성을 보장하지 않는다.

## 채팅과 세션

- 세션을 처음 표시하거나 다른 세션으로 전환할 때만 대화의 맨 아래로 이동한다. 이후 새 답변·사고 내용·도구 결과가 와도 자동으로 하단을 따라가지 않고 읽던 텍스트 위치를 유지한다.
- 대화 내용은 마우스로 드래그해 선택한 뒤 `Ctrl+C` 또는 우클릭 `선택 영역 복사`로 복사한다. 작업 중에도 복사를 허용한다. 드래그 중 화면 재작성을 미루고 기존 텍스트가 같으면 선택 범위를 보존한다. 사고/작업 기록 버튼은 클릭 후 놓을 때 열고 닫으며, 드래그 선택은 토글로 처리하지 않는다.

- 사용자 메시지와 답변을 구분하고 제목·굵은 글씨·목록·코드 서식을 표시한다. 진행 문구와 도구·승인 기록은 `작업 기록`을 눌러 펼친다. 원문은 오른쪽 Tools 탭과 세션 파일에 보존한다. 대화 위쪽을 읽는 중에는 자동으로 맨 아래로 이동하지 않는다. 대화 상단 복사 버튼은 마지막 답변 원문을 복사한다.
- 답변 아래에 서버 실측 `입력 tok/s · 출력 tok/s`와 `이번 추론 · 답변까지` 시간을 표시한다. 속도는 해당 모델 호출의 입력 처리/출력 생성 속도이며, 답변까지 시간은 현재 요청의 모델 로딩·도구·승인 대기를 포함한다. 여러 도구 호출이 있었으면 최종 답변 아래 속도는 마지막 호출 기준이다. 각 호출 수치는 작업 기록에 있다. 캐시된 입력 전체를 경과 시간으로 나누어 속도를 부풀리지 않으며, 예전 기록처럼 서버 측정값이 없으면 `미측정`으로 표시한다.
- 새 답변마다 시스템이 `컨텍스트(입력+출력): 4,100 / 8,192 tok (서버 보고)`처럼 해당 모델 호출의 전체 입력 토큰과 생성 출력 토큰 합계, 당시 설정 한도를 저장·표시한다. 모델에게 숫자를 작성시키지 않는다. 서버 usage가 있으면 이를 우선하며, 캐시 포함 입력을 사용하고 출력에 포함된 추론 토큰을 다시 더하지 않는다. Claude의 별도 캐시 읽기/생성 입력은 입력 합계에 포함한다. 세션 전체 누적 과금량이나 실제 KV 메모리 사용량, 다음 요청의 문맥 길이를 의미하지 않는다. 이미지가 다음 요청에서 빠지거나 오래된 문맥이 제외되면 값이 줄어들 수 있다.
- usage가 없거나 일부만 있으면 기존 문맥 토큰 계산과 답변 추가 전후 차이로 보완하고 `추정`을 붙인다. 이미지 입력량을 보고받지 못한 경우 기존 예약값1536토큰을 추정에 더한다. 추가 토큰 계산에 실패하면 출력은 UTF-8 바이트 수 기반으로 추정해 답변 저장이 실패하지 않게 한다. 따라서 추정값은 채팅 템플릿·이미지·도구 규격의 실제 모델 토큰과 다를 수 있다. 여러 단계의 작업은 마지막 답변 생성 호출 기준이며, 각 중간 호출 수치는 작업 기록에 남는다. 과거 답변에 없는 사용량은 소급 생성하지 않으며, 표시값은 설정 변경·앱 재시작 후에도 해당 답변 당시 값으로 유지한다.
- 왼쪽 `+`는 새 세션, 연필은 이름 변경, 내려받기 버튼은 세션 JSON 내보내기다. 과거 세션을 선택한 뒤 새 메시지로 이어갈 수 있다.
- 각 사용자 메시지와 최종 답변의 `⋯`를 누르거나 본문을 우클릭하면 **편집·삭제·이 요청 재실행** 메뉴가 열린다. 편집 창에서 여러 줄을 수정하고 하단 `확인`으로 저장한다. 버튼 영역은 창을 줄여도 유지하며 사용자 메시지는 `저장 후 재실행`도 가능하다. 편집된 메시지는 표시되며 기존 실제 도구 기록을 바꾸거나 작업을 자동으로 다시 수행하지 않는다. 작업 실행 중에는 변경을 막는다.
- 사용자 메시지 삭제는 그 요청의 답변·도구·승인 기록까지 다음 사용자 요청 전 구간을 삭제한다. 최종 답변 삭제는 해당 답변만 삭제한다. 다른 대화 구간은 유지하며, 도구 호출 자체를 답변처럼 편집하지 못하게 한다. SQLite와 세션 로그를 함께 갱신한다. 메시지 삭제만으로 저장 파일이나 이미 실행된 외부 작업을 지우거나 되돌리지는 않는다.
- 재실행은 **같은 세션**에서 선택한 사용자 요청 또는 답변에 대응하는 요청과 그 이후 답변·도구·후속 대화를 삭제하고, 해당 요청을 다시 추가해 실행한다. 요청 이전 문맥과 세션 ID·제목은 유지하며 새 세션을 만들지 않는다. 삭제 전 재사용할 첨부가 현재 세션 안에 존재하는지 검사한다. 삭제된 대화는 복구하지 못하며 재실행이 실패해도 과거 답변을 복원하지 않는다. 저장 파일은 세션 삭제까지 남지만 삭제된 기록의 첨부는 모델에 자동 재첨부하지 않는다. 확인 후 현재 모델/권한으로 실행하므로 클릭·입력 등의 부작용이 반복될 수 있다. 관리형 브라우저와 외부 앱의 실제 상태는 과거로 되돌리지 않는다.
- 세션 목록 아래 `×`는 현재 세션 삭제다. 확인 후 브라우저와 작업을 닫고 대화 DB 레코드, 첨부 복사본, 캡처·영상·로그, 세션 브라우저 프로필을 삭제한다. 첨부 원본과 별도로 내보낸 파일, 다른 세션은 건드리지 않는다. 마지막 세션을 지우면 빈 새 세션을 만든다. 복구 기능이나 보안 덮어쓰기를 제공하는 삭제는 아니다. 파일이 열려 있어 삭제하지 못하면 오류로 알리며 세션 DB는 유지한다.
- 대화·도구 호출·결과·승인 기록은 `data/sessions.sqlite3`에 저장된다. 중단된 응답은 부분 응답으로 표시하며 완료된 답변처럼 모델에 재전달하지 않는다.
- 전체 기록은 SQLite와 세션의 `history.jsonl`에 보존한다. 모델용 이력은 `{"tool":"desktop_capture","status":"delivered","id":12,"result":{"bounds":[...]},"image":"..."}`처럼 단층 JSON으로 만든다. JSON 결과를 다시 문자열로 감싸거나 도구명·상태를 메타데이터에 중복하지 않는다. 같은 영상 경로·오류는 한 번만 넣으며, 정상 캡처·클릭의 반복 안내와 bounds로 알 수 있는 캡처 width/height는 제외한다. 좌표 기준·경계·클릭 진단·파일 경로·작업 ID·브라우저 선택자는 유지한다. 정상 승인(automatic/confirmed) 로그는 모델용 이력에서 제외하지만 원본에는 보존하고, 거부·오류·중단·부분 실행은 유지한다.
- 긴 정상 결과의 텍스트만 일반1800자/브라우저1200자로 줄여 `excerpt:true`와 원본 `id`를 붙인다. 구조화된 결과의 다른 필드와 브라우저 선택자 목록, 오류·중단 결과, 명시적 `file_read`/`session_history` 페이지는 개별 본문을 자르지 않는다. 단, 문맥 한도가 부족하면 아래 규칙에 따라 해당 기록 전체가 전송에서 제외될 수 있다. `files` 도구군의 `session_history`에서 원문을 조회할 수 있고 파일은 작은 offset/limit 페이지로 읽을 수 있다. 요약과 전송 제외 모두 저장 원문을 삭제하지 않는다.
- 고정 지침·권한·로드된 도구 목록은 시스템 메시지 앞부분에 유지하고 대상 창·로그 경로·이미지 유무·미완료 작업·직전 결과·남은 단계·반복 경고·문맥 제외 수는 **이력 뒤의 상태 메시지**로 보낸다. 상태 메시지는 매 요청에 한 번 만들며 과거 기록으로 누적하지 않는다. 내부 네이티브 호출 연결용 필드는 실제 전송과 텍스트 토큰 계산에서 제외한다. 상태·도구 결과는 새 사용자 요청이 아니며 안에 있는 이름·문구를 지시로 신뢰하지 않도록 안내한다.
- 로컬 `cache_prompt:true`는 유지한다. 같은 도구 목록·권한 아래에서는 상태만 바뀌어도 시스템/기존 이력 접두부가 같아 KV 재사용에 유리하다. 도구군 로드·권한/effort 변경·오래된 문맥 제외·메시지 편집은 접두부를 바꿀 수 있다. 서버 종료 후 캐시를 복원하거나 세션별 KV를 디스크에 저장하는 기능은 추가하지 않았다. 외부 API 캐시 정책은 제공자에 따른다.
- 문맥이 한도를 넘으면 **가장 오래된 사용자 대화 묶음부터** 전송에서 제외하고 다시 계산한다. 직전 대화도 예외 없이 제외할 수 있다. 현재 요청 안의 도구 기록만으로 너무 길어지면 현재 사용자 요청은 유지하고 오래된 도구 호출·결과 묶음부터 제외한다. 하나의 큰 도구 결과도 필요하면 호출과 함께 제외하므로 이력 누적만으로 작업을 중단하지 않는다. 제외 사실과 원문 조회 안내를 마지막 상태에 넣고 불확실한 동작을 반복하지 않도록 안내한다. 도구 호출과 결과를 가급적 함께 제거해 네이티브 API의 연결을 유지한다.
- 제외된 원문은 대화창에서 그대로 보이며 **`문맥 제외: 마지막 모델 요청에 미포함`**을 표시한다. 접힌 작업 기록에는 제외된 기록 수, 펼친 기록에는 개별 제외 표시가 붙는다. 마지막 문맥 구성의 제외 ID·계산량·한도는 세션별 별도 테이블에 저장하므로 재시작 후에도 표시된다. 다음 요청에서 한도가 늘어나 재포함되면 표시를 갱신한다. 메시지 편집·삭제·재실행은 오래된 표시를 초기화하고 다음 요청에서 재계산한다. 표시가 없는 새 답변까지 이전 요청에 포함됐다는 뜻은 아니다.
- 시스템 지침·현재 사용자 요청·필수 상태만으로도 한도를 넘으면 이전 기록을 모두 제외해도 요청을 만들 수 없다. 이 경우에만 현재 요청을 줄이거나 컨텍스트를 늘리라는 안내를 한다. 현재 사용자 요청을 임의로 잘라 의미를 바꾸거나 안전 지침을 제거하지 않는다. 모델은 제외된 대화를 기억한다고 가정하지 않으며 필요하면 저장 기록을 다시 조회해야 한다.
- `Reasoning`은 로컬 추론 켜기/끄기다. **Qwen3.8 27B(IQ2_S/IQ2_XXS 포함)는 `low / medium / xhigh`를 `reasoning_effort`로 전달**하며 OFF는 `none`이다. 공식 템플릿은 `high`를 지원하지 않으므로 목록에 넣지 않는다. 숫자 사고 예산을 전달하지 않고 서버도 `--reasoning auto --reasoning-format deepseek`로 구동한다. 상단에서 사고 수준이나 ON/OFF만 변경하면 재로드 없이 다음 요청에 적용되며 로컬 설정창의 `reasoning_tokens` 입력도 `reasoning_effort` 선택기로 바뀐다. 이전 설정 파일은128이하→low,256이하→medium,그 이상(high/extended)→xhigh로 읽어 오되, 기존 파일은 저장하기 전까지 수정하지 않는다.
- 로컬 요청의 `max_tokens=-1`로 전체 출력 상한을 제거했다. 문맥 예약에 사용하는2048·768 등의 값은 이력 정리에 필요한 여유 공간일 뿐 생성 종료 조건이 아니다. Qwen의 low/medium/xhigh를 숫자 토큰 수로 치환하지 않는다. 다른 로컬 모델도 사고ON에서는 `--reasoning-budget -1`을 사용하고 화면에 `Unlimited`로 표시한다. 기존 숫자 설정은 호환용이며 출력 길이를 제한하지 않는다. xhigh가 정확도 향상을 보장하지 않고, 엔진이 문맥 용량 등으로 응답을 중단하면 미완료 호출은 실행하지 않는다. 외부 API 설정은 별도다.
- 서버가 반환한 사고 내용은 **채팅 내부의 `[사고중]` 버튼**으로 펼치고 접는다. 기본은 접힌 상태이며 열어 둔 경우 실시간으로 갱신한다. 답변이 저장되면 답변 위의 `[사고 내용]`으로 바뀌고 해당 요청에서 선택한 펼침 상태를 유지한다. 다음 요청은 다시 접힌 상태로 시작한다. 오른쪽 사고 탭과 별도 팝업은 사용하지 않는다. 이 버튼은 표시만 켜고 끄며, 상단 `Reasoning`의 추론 실행 설정과는 별개다. 중간 도구 호출의 사고 내용은 `작업 기록`을 펼친 뒤 같은 인라인 버튼으로 연다. 저장된 대화에서도 응답별로 열 수 있고 로컬 응답 수신 중 실패·취소되면 이미 받은 내용은 `미완료`로 표시한다. 서버가 반환하지 않은 내용을 복원하거나 만들어 표시하지 않으며, 외부 API는 제공자가 공개한 내용/요약만 표시한다. 로컬 사고의200000자 수신 제한은 제거했고 화면 미리보기 제한은 유지한다. 다음 모델 요청에는 자동 재첨부하지 않는다. 대화와 함께 로컬 DB에 저장되므로 민감한 내용이 있을 수 있다.
- 설치된 llama-server `b11000-60199339b`와 Qwen 27B IQ2_S GGUF에서 low/medium/xhigh의 템플릿 결과가 서로 다름을 확인했다. 합성 요청의 low는 사고102자와 정상 답변, none은 사고0자와 정상 답변을 반환했고 두 요청은 같은 서버를 재사용했다. 서버 실행 인수에 사고 budget이 없음을 확인했으며, 실제 계정·사용자 화면·도구 입력·외부 API 요청은 사용하지 않았다.
- 설정 톱니바퀴의 `context_tokens`에서 컨텍스트를4096~65536 범위,1024단위로 변경한다. 기본8192이며 변경 시 서버를 내리고 다음 로드의 `-c` 옵션과 문맥 예산에 함께 반영한다. **큰 문맥은 VRAM/RAM 증가, 느려짐, 서버 로드 실패를 유발할 수 있다.** 선택 가능한 상한이 해당 GPU에서의 동작 보장을 뜻하지 않는다. 작은 문맥은 도구 안내와 직전 기록조차 들어가지 않을 수 있다. 게임 에이전트 설정은 바꾸지 않는다.
- 입력창 왼쪽 대각선 화살표는 한 줄 모드 전환이다. 입력·보내기·중단·복원만 남고 세션/대화 상태는 유지한다. 승인 요청이 생기면 전체 창으로 자동 복원한다.
- 한 작업은 기본20단계/약10분 제한이다. 새 이미지가 있는 요청에는 즉시 그 이미지를 사용하도록 안내한다. 동일 도구·인수가 반복되면 기존 결과 사용 또는 마무리를 안내하고, 네 번째 호출은 실행하지 않은 채 남은 단계 한도 안에서 한 번 수정 응답 기회를 준다. 다시 반복하면 중단한다. 중복 클릭을 추가 실행하거나 무제한 재시도하지 않으며 모델의 반복 자체가 항상 해결된다는 보장은 없다. 단계 한도는 설정에서 변경 가능하다.

## 도구와 승인

### 이미지 크기와 좌표

오른쪽 `Model image`에서 `Max 1280px` 또는 `Original`을 선택한다. 기본1280px는 긴 변이1280px를 넘을 때만 비율을 유지해 축소하며, `Original`은 앱 단계의 축소를 하지 않는다. 설정은 로컬 모델과 외부 API 모두에 적용되고 다음 요청부터 사용된다. 선택해도 모델이나 사고 수준을 바꾸지 않는다. 이미지 토큰 한도·비전 인코더 내부 리사이즈는 별개이며 원본 전송이 곧 원본 해상도 인식을 보장하지 않는다. 녹화와 영상 대표 프레임 자체의 해상도 제한은 유지된다.

그 아래 `Capture margin`은 선택 창 주변을 함께 볼 여백이며 `0 px`(기본), `128 px`, `256 px`, `512 px`를 선택한다.0은 기존 HWND 직접 렌더링, 양수는 선택 창의 보이는 영역을 사방으로 확장해 **실제로 보이는 화면**을 캡처한다. 모니터 전체 범위에서 잘라내고 포커스를 옮기지 않는다. 다른 창·겹친 창·주변 개인정보가 포함될 수 있어 꺼진 상태에서 켤 때 확인한다. 외부 API 사용 시 주변 화면도 함께 전송될 수 있다. 설정은 저장되며 다음 정지 캡처부터 적용된다. 입력 권한은 선택 창 안으로만 제한하고 주변 이미지의 픽셀도 프로그램이 환산한다. 창 이동·크기 변경 시 다시 캡처해야 한다. 녹화는 기존 HWND 전용 방식이며 이 여백 옵션을 적용하지 않는다. 선택 창이 없으면 기존처럼 전체 화면 캡처다.

새 데스크톱 좌표는 **전송한 이미지의 픽셀**이다. `(0,0)`은 이미지 왼쪽 위이며 모델에게 정규화 계산이나 화면 위치 오프셋 덧셈을 요구하지 않는다. 호출에 `coordinate_space:"image_pixels"`를 명시하고 프로그램이 원본 영역으로 환산한다. 상태와 첨부 이미지에 전송 폭·높이를 전달하며, 이미지가 아직 없으면 선택 창의 물리 픽셀 영역을 기준으로 한다. 사전 캡처 자체를 항상 강제하지는 않는다.

선택 창 캡처·전체 화면 캡처의 기준을 구분한다. 전체 화면의 점도 선택 창 내부로 매핑되는 경우에만 허용하고, 다른 창/PID 또는 이동·크기 변경된 창, 이미지 범위를 벗어난 시작점/끝점은 입력 전에 거부한다. 임의 파일 이미지·관리형 브라우저·영상 합성 프레임은 데스크톱 클릭 참조로 추측해 쓰지 않으므로 필요한 경우 대상 창을 다시 캡처한다. 키보드 입력과 CSS 선택자 기반 브라우저 도구는 기존 방식을 유지한다. 이전 저장 호출의0..1000좌표는 명시적 픽셀 호출과 구분해 읽으며 새 모델 호출에서 기준이 누락되면 실행하지 않는다.

### 간단 호출과 도구군

모델에게는 `tool`, `arguments`만 요구한다. 예를 들어 `{"tool":"desktop_click","arguments":{"x":250,"y":500,"coordinate_space":"image_pixels"}}`는 기준 이미지의(250,500) 픽셀을 왼쪽 버튼으로1회 클릭하는 요청이다. 답변은 `{"tool":"finish","arguments":{"text":"확인한 내용"}}`이다. 진행 문구·내부 위험 표시·기본값은 실행기가 보충한다. 이전4필드 기록과 실행기 내부 검증 형식은 호환성을 위해 유지하지만 모델에게 생성하도록 요구하지 않는다. 알 수 없는 필드·잘못된 값·권한 없는 호출을 추측해 고쳐 실행하지 않는다.

- 기본 목록은 답변·도구군 로드·창 선택·캡처·일반 입력의 최대11개다. 권한이 꺼진 도구는 안내와 출력 규격에서 빠지고 실행 전에도 차단된다.
- 짧은 기능 안내는 항상 제공한다. `browser`는 관리형 웹 탐색, `recording`은 녹화·작업 제어, `advanced_input`은 키 큐·길게 누르기·고급 입력, `files`는 첨부·영상·전체 기록 조회다.
- `{"tool":"load_tool_group","arguments":{"groups":["recording"]}}`로 필요한 규격을 로드한다. 권한을 켜거나 녹화를 시작하지 않으며 로드한 도구군은 현재 작업 동안 유지된다. 작업 종료 후 새 요청에서는 다시 선택한다.
- 요청에 녹화·파일·브라우저 등 명시적 단서가 있으면 해당 도구군을 미리 로드한다. 첨부가 있으면 파일 도구를 미리 제공한다. 이 분류가 놓쳐도 모델이 직접 로드할 수 있다.
- 버튼/클릭수·입력 모드·녹화 fps·키 지연·파일 offset/limit 등의 기본값은 실행기가 채운다. 고급 입력은 해당 종류에 필요한 key/text/좌표만 지정하면 된다. 메시지 입력의 좌표처럼 필요한 값은 생략할 수 없다.
- 스크롤은 데스크톱·브라우저 모두 `direction: "up" | "down"`과 양수 `amount`로 통일하고 기존 내부 부호로 변환한다.
- 프롬프트에는 현재 대상·이미지 유무·로드된 도구군·직전 도구/상태·미완료 작업·남은 단계를 제공한다. 도구 결과는 사용자 요청과 구분한 불신 데이터 봉투로 전달하며, 네이티브 API 모드에서만 실제 `tool` 역할로 변환한다.
- 이미지의 다음 요청1회 사용 정책은 유지한다. 도구군은 가능한 캡처 전에 로드하며, 캡처 이후 도구군 로드에 그 요청을 사용하면 이미지를 다음 요청에 몰래 다시 넣지 않는다.

관측 ID는 없다. 캡처·클릭·키 입력 사이의 필수 선행 관계도 없다. 필요할 때 모델이 캡처를 요청할 수 있지만 사전 캡처 없이 클릭/입력 도구를 쓸 수도 있다.

Tools의 캡처·입력·관리형 브라우저·일반 작업 자동 승인 체크는 기본으로 켜진다. 시작하는 것만으로 도구를 실행하지는 않는다. 필요 없는 권한은 메시지를 보내기 전에 해제한다. `Target window`는 직접 선택하거나 모델이 `window_list`로 현재 창 목록을 읽고 `window_select(handle,pid)`로 변경할 수 있다. 모델이 바꾸면 UI 선택도 갱신한다. 자체 앱 창은 목록에서 제외하며 닫혔거나 PID가 달라진 창은 거부한다. 대상 변경도 승인 정책을 적용한다.

일반 데스크톱 입력은 창 PID·포커스·영역을 검사하고 입력 전 대상 창을 앞으로 가져온다. 창 전체의 모서리가 모두 가려지지 않아야 한다는 게임용 검사는 사용하지 않는다. 대신 실제 클릭·드래그 지점이 다른 창에 가려져 있거나 대상 창이 바뀌면 입력을 차단한다. 최소화된 창만 복원하며 최대화된 창은 크기를 유지한다. 새 좌표는 위의 **이미지 픽셀 기준**을 사용한다. DWM 프레임 경계를 사용하고 조회가 불가능할 때만 GetWindowRect를 사용하며, 고정8px 테두리 잘라내기는 없다. 작업 스레드의 DPI 모드와 관계없이 캡처·일반 입력·창 메시지 입력이 같은 물리 픽셀 기준을 사용한다. 과거 캡처/로그의 정규화 좌표를 픽셀로 그대로 재사용하지 않는다. 메시지 방식 입력은 아래 예외를 따른다.

`desktop_click` 결과에는 진단용으로 `coordinate_space`, `pixels`(전송 이미지 픽셀), `bounds`(클릭 당시 창 경계), `requested_desktop`(변환한 화면 픽셀), `pointer_before_press`(각 버튼 누르기 직전 표본), `pointer_after_action`을 기록한다. 이전 정규화 호출은 `normalized`로 구분한다. `desktop_input`의 일반/장치 클릭도 이 경로를 사용한다. 표본은 앱이 실제 어느 컨트롤을 처리했는지 증명하지 않으며 표본 사이 사용자가 포인터를 움직일 수도 있다. 이 진단을 위해 모델의 위치 추정을 임의로 보정하지 않는다.

픽셀 전환 후 원본/축소를 번갈아 사용한 실제 합성 창10개 지점(음수 좌표 모니터 포함)은 캡처 픽셀부터 클릭 수신까지 최대1px 오차였다. 모델의 위치 선택은 별개다. 실제 IQ2_S 합성 확인에서는392x642 원본 및1920x1080 원본의 버튼은 맞췄으나1280x720 축소 이미지에서는 빗나갔다. 세 경우 모두 픽셀 규격을 반환했고 실제 모델 클릭은 실행하지 않았다. [모델 픽셀 응답 원자료](data/benchmarks/pixel-input-smoke-20260919-144545/results.json)를 남겼다. 픽셀 전환이나 원본 선택이 시각적 판단 오류를 없앤다는 의미는 아니다. 이전 양자화 연구의 좌표 품질 결과는 정규화 규격 당시 기록이며, 현재 재실행하는 품질 과제는 픽셀 규격이다.

2026-09-19 합성 테스트에서 제목 표시줄을 포함한 창을 실제 캡처한 뒤 모델용 JPEG1280px로 축소하고 표식 중심을0..1000으로 변환해 실제 클릭을 전달했다. 일반 위치와 음수 좌표 모니터의10개 지점 모두 앱이 수신한 위치의 오차가 최대1픽셀이었다. 별도로 현재 IQ2_S·12K·추론OFF·이미지1024토큰 모델에 합성 버튼3개를 보여 줬을 때 중심 오차는 각각(-5,-3), (3,-5), (-4,-1)픽셀이며 모두 버튼 내부였다. 모델이 생성한 클릭은 실행하지 않았다. 실제 사용자 화면·개인 대화는 이 검증에 사용하지 않았고, 다른 앱의 캡처 방식·혼합 DPI·작은 버튼 인식·상태 변경·과거 오클릭의 원인까지 검증한 결과는 아니다.

`desktop_key_queue` / `browser_key_queue`는 키와 지연 시간을 한 번에 전달한다. 예를 들어 "Tab을 누르고 300ms 뒤 Tab, 500ms 뒤 Enter를 입력해"라고 요청할 수 있다. `steps`는 `[{"key":"Tab","delay_ms":0},{"key":"Tab","delay_ms":300},{"key":"Enter","delay_ms":500}]` 형태이며 지연은 **각 키를 누르기 전** 시간이다. 최대32단계, 단계당0~5000ms, 총 지연60초까지 허용한다. 큐 내부의 위험 키도 승인 대상이며 브라우저는 매 단계의 실제 포커스 대상을 재검사한다. F8/Stop으로 남은 입력을 취소할 수 있지만 이미 입력한 키는 되돌리지 않는다. UI/OS 처리 시간 때문에 지연은 정밀 실시간 타이머가 아니다.

일반/장치 방식 키 입력은 같은 HWND·PID·포커스를 유지하면 창 이동·크기 변경만으로 중단하지 않는다. 마우스 입력은 좌표가 달라지면 계속 차단한다. 키 큐 도중 다른 창이 활성화되면 남은 키를 보내지 않고 완료된 단계 수와 중단 원인을 알린다. 현재 단계의 일부 키가 이미 전달됐을 수 있으므로 전체 큐를 자동 재실행하지 않는다. Enter로 새 창이 열린 경우 대상 창을 다시 확인한 뒤 이어서 요청해야 한다.

브라우저는 별도 Playwright Chromium을 사용한다. 세션별 `artifacts/<session-id>/browser-profile`에 브라우저 데이터가 저장되며 개인 브라우저 프로필을 가져오지 않는다. HTTP(S) 이동, 검색, 페이지 텍스트/선택자 읽기, CSS 요소 클릭/입력, 키, 스크롤, 뒤로가기, 탭 선택을 지원한다. 읽기는 텍스트만 반환한다. 파일 업로드·비밀번호 입력·다운로드·브라우저 대화상자 확인은 자동으로 처리하지 않으며 사용자가 직접 해야 한다. 모델이 임의 코드를 실행하는 shell/JavaScript 도구는 제공하지 않는다.

선택한 일반 Chrome 창과 관리형 브라우저는 서로 다르다. 일반 Chrome의 내용을 보려면 `desktop_capture`를 사용한다. 관리형 `about:blank`를 읽어서는 일반 Chrome의 내용을 가져올 수 없다. 모델에 이 구분과 빈 페이지 안내를 전달한다. 화면 전사는 캡처를 본 뒤 답변하도록 안내하지만, 작은 글씨 인식이나 임의 페이지의 정확한 전사를 보장하지는 않는다.

기본으로 켜진 `Auto-approve routine tasks`는 일반 탐색·읽기·클릭·타이핑과 Enter/Tab/일반 단축키를 자동으로 진행한다. 끄면 실행 작업마다 승인한다. Delete, Shift+Delete, Alt+F4, Ctrl+W, Ctrl+Enter 및 삭제·결제·외부 전송·게시·권한 변경 등으로 식별된 작업은 계속 확인한다. 필수 `risk` 문자열 대신 원래 사용자 요청의 민감 작업 표현·실제 인수·브라우저 대상 문구와 폼을 실행기에서 검사한다. 오래된 sensitive 표시는 추가 승인 사유로 유지한다. 일반 Enter 자체는 승인 사유가 아니지만 실제 전송/삭제 맥락이면 확인한다. 요청 의도 검사는 작업 전체에 적용하므로 보수적으로 승인 횟수가 늘 수 있다.

**자동 승인은 보안 샌드박스가 아니다.** 키워드·DOM·모델 분류가 업무의 실제 의미를 완벽히 알아내지는 못하며, 특히 데스크톱 클릭/Enter가 예상치 않은 영향을 줄 수 있다. 민감한 계정·자료·결제 창에서는 항상 확인 모드를 사용하고 실행 내용을 직접 검토해야 한다. 승인한 입력의 게임/앱 효과까지 자동으로 입증하지 않는다. 화면과 웹페이지는 불신 데이터로 안내하지만 프롬프트 인젝션을 완전히 차단한다고 보장하지 않는다.

Stop 버튼 또는 F8/Esc로 중단한다. 모델 추론 중 중단은 앱이 소유한 모델 프로세스를 종료하므로 다음 요청에서 재로드한다. 이미 전달된 입력은 되돌리지 못한다. 진행 중 브라우저 호출은 해당 호출의 제한 시간(보통5~15초)까지 정리 지연이 있을 수 있다. 사용자 메시지 없이 자동 재시작하지 않는다.

## 캡처 수명

- "지금 내가 보고 있는 화면을 그대로 캡처해"라고 요청하면 `desktop_screen_capture`로 전체 가상 데스크톱을 캡처한다. **Target Window가 없어도 되며 어떤 창도 앞으로 가져오거나 복원·이동하지 않는다.** 여러 모니터, 작업 표시줄, 현재 보이는 다른 창과 Local Desk 자체도 포함될 수 있다. `Window capture / video` 권한을 사용하며 마우스/키보드 권한은 필요 없다. 선택 창만 캡처하려면 기존 `desktop_capture`를 사용한다.
- `Capture margin=0 px`에서 `desktop_capture`는 화면의 사각 영역을 잘라 오는 대신 **선택한 HWND를 PrintWindow로 직접 렌더링**한다. 포커스를 옮기지 않으며 다른 창이나 Local Desk가 위에 겹쳐 있어도 그 겹친 창을 담지 않는다. 양수 여백은 위에서 설명한 실제 화면 캡처로 명시적으로 전환한다. 선택된 창이 없으면 전체 화면 캡처로 처리한다. 최소화되거나 완전히 화면 밖에 있는 창은 거부하며, 일부만 화면 안에 있으면 화면과 겹치는 프레임 영역을 사용한다. 이 동작은 로컬/API 모드에서 동일하다.
- 창 렌더링은 보조 프로세스에서 실행하며 호출당3초 제한과 중지 처리를 적용한다. 창이 응답하지 않거나 캡처에 실패하면 오류를 알리고 보조 프로세스를 정리한다. 실패를 숨기고 옆 화면이나 데스크톱 사각 영역으로 대체하지 않는다. 앱이 PrintWindow를 지원하지 않거나 보호된/하드웨어 가속 콘텐츠를 제공하지 않으면 실패하거나 검은 이미지가 나올 수 있으며, 검은 이미지의 자동 판별은 제공하지 않는다. 현재 보이는 화면이 필요하면 `desktop_screen_capture`를 명시적으로 사용한다.
- 전체 화면의 좌표는 선택 창 내부 좌표와 다르므로 그 값을 선택 창 입력 도구에 그대로 사용하면 안 된다. 매우 큰 다중 모니터 화면은 모델 입력용 축소 이미지에서 작은 글씨가 읽히지 않을 수 있다. 보관 PNG는 원본 해상도다.
- `desktop_capture`, `desktop_screen_capture`, `browser_capture`, `desktop_record`, `browser_record`의 결과를 받거나 `file_view`를 명시적으로 호출한 경우에만 이미지가 모델에 들어간다. 일반 브라우저 읽기·이동·클릭과 파일 경로 조회는 스크린샷을 자동 첨부하지 않는다.
- 캡처 직후 **다음 모델 요청 한 번**에만 이미지 한 장을 첨부한다. 이후 도구/대화 요청, 다른 세션, 재개된 세션에는 과거 이미지를 넣지 않는다. 텍스트 관찰 결과는 대화 기록으로 남을 수 있다.
- 정지 캡처 PNG는 원본 해상도로 세션의 `data/artifacts/<session-id>/`에 보관한다. 모델에는 가로세로 비율과 양쪽 끝을 유지해 축소한 사본을 보내며, 축소를 위해 일부를 잘라내지 않는다. 오른쪽 `Captures / videos`에서 PNG/MP4 선택 후 열기/더블클릭으로 볼 수 있다. 사용자 열람은 모델 재첨부를 일으키지 않는다.
- 캡처 미리보기에 이전 이미지가 남아 있어도 모델에 계속 전달된다는 뜻은 아니다. 저장 파일에는 화면상의 개인정보가 포함될 수 있다. DB·캡처·브라우저 프로필은 암호화하지 않는 로컬 파일이며 이 앱은 자동 삭제하지 않는다.

## 파일 첨부

입력창 옆 `+` 메뉴에서 파일을 고르거나 탐색기에서 앱/입력창/대화창으로 끌어 놓는다. 공백·한글 경로를 지원한다. 보내기 전에 메뉴에서 개별 파일을 제거할 수 있다. 메시지 없이 첨부만 보내도 된다. 세션을 바꾸면 아직 보내지 않은 첨부는 비운다.

첨부는 전송 시 세션의 `attachments` 폴더에 복사한다. 한 메시지에 최대8개, 파일당100MB, 합계200MB이다. 파일명·저장 경로·크기·형식은 모델에 전달하며, 내용은 모델이 `file_read` 또는 `file_view`를 호출해 읽는다. 텍스트/코드/CSV/JSON/PDF/DOCX는 텍스트 추출, 이미지·영상은 명시적 시각 열람을 지원한다. PDF는 텍스트가 있는 문서용이며 암호화 문서는 잠금 해제된 사본이 필요하다. 스캔 PDF의 OCR, HWP 등 기타 바이너리 형식 해석은 지원하지 않는다. 알 수 없는 파일은 메타데이터만 보관하고 실행하지 않는다.

읽기 도구는 현재 세션에 등록된 첨부/캡처 파일만 허용한다. 이미지·영상 열람 결과도 다음 모델 요청 한 번만 사용하며, 다음 대화에서 자동 재첨부하지 않는다. 첨부 내용은 불신 데이터로 취급한다.

## 병행 실행

"Chrome을 녹화하면서 다음 버튼을 클릭해"처럼 요청할 수 있다. `{"tool":"desktop_record","arguments":{"seconds":5,"background":true}}`처럼 일반 도구의 인수에 `background:true`를 지정하면 실행기가 작업 큐를 만들며 중첩 `job_start` 규격을 모델에게 요구하지 않는다. 기본은 동기 실행이다. 완료된 작업은 다음 모델 요청 전에 자동으로 수집하고, 최종 답변 직전에도 남은 결과를 수집해 모델이 검토하도록 한다. `recording` 도구군의 `job_status`/`job_result`/`job_cancel`로 명시적 조회·대기·개별 취소도 가능하다. 동시에 보관할 수 있는 미수집 작업은 최대4개이다. 녹화 준비가 됐는지 확인한 뒤 상호작용해야 시작 장면을 놓치지 않는다. 입력은 병행 요청해도 기존 입력 lane에서 직렬화한다.

브라우저 녹화는 같은 탭에 독립적인 로컬 CDP 연결을 사용해 클릭·입력과 겹쳐 진행된다. CDP 포트는127.0.0.1의 임시 포트이며 개인 브라우저에 연결하지 않는다. 같은 브라우저의 제어 명령과 같은 전역 키보드/마우스 입력은 충돌 방지를 위해 각각 직렬화한다. 따라서 모든 입력을 무조건 동시에 섞는 방식은 아니다. 물리 포인터를 쓰는 여러 창의 동시 제어에는 제약이 있다.

각 작업은 시작 시점의 대상/권한을 고정해 사용한다. 이후 Target Window 변경이 이미 진행 중인 작업을 다른 창으로 돌리지는 않는다. 승인 요청은 한 번에 하나씩 표시한다. 개별 취소는 다른 작업을 취소하지 않으며, 전체 Stop/F8·세션 종료는 남은 작업을 취소하고 결과를 정리한다. 최종 답변 전 미수집 작업은 수집하며 실패/부분 녹화도 기록한다. 작업 결과 이미지 여러 개를 한꺼번에 수집한 경우 다음 요청에는 마지막 이미지 한 장만 전송하고 모든 경로/결과는 남긴다.

## 입력 방식

`desktop_input(mode, kind, ...)`는 다음 방식을 구분한다. 기존 클릭·키 큐 도구도 유지한다.

| mode | 동작 | 주의점 |
|---|---|---|
| general | 전경 창에서 가상 키·Unicode와 SendInput 마우스 입력 | 키보드는 현재 입력 위치, 마우스는 지정 좌표 |
| device | 키보드 스캔코드·SendInput 마우스 | 소프트웨어 주입이며 실제 USB/HID 장치 신호가 아님. 임의 Unicode 타이핑은 general 사용 |
| message | 지정 좌표의 Win32 자식 컨트롤에 창 메시지 전달 | 포인터·전경 포커스를 옮기지 않음. 앱이 메시지를 무시할 수 있으며 Chrome/게임 호환성 보장 없음 |

message 모드의 텍스트는 해당 컨트롤의 기존 캐럿에 들어간다. 컨트롤 내 임의 문자 위치까지 자동 지정하는 기능은 아니다. 최소화된 창은 좌표 매핑 때문에 거부한다. 수정자 조합은 실제 키 상태를 재현하지 못하므로 일반/device 모드를 사용한다. 권한·위험 키 확인은 모든 방식에 적용하며 실패 시 다른 방식으로 몰래 우회하지 않는다.

`desktop_hold`는 마우스 버튼 또는 키/조합을1~10000ms 유지 후 해제한다. 예: "W키를 장치 방식으로 2초 눌러줘", "이 지점에서 왼쪽 버튼을 1초 유지해". `desktop_drag_timed`는 시작/끝 좌표와50~10000ms 이동 시간을 받아 드래그한다. 둘 다 general/device/message를 선택할 수 있다. 문자·숫자·기능 키 F1~F12·기존 단축키를 지원하며 키를 누른 뒤 놓기까지 한 도구 안에서 수행한다. 키/버튼을 여러 모델 요청 동안 무기한 눌러두는 기능은 제공하지 않는다.

관리형 브라우저는 `browser_hold`로 요소의 마우스/키를 유지하고 `browser_drag`로 요소 사이를 지정 시간에 드래그한다. 각 도구는 중단·예외 시 눌린 키/버튼을 해제하며 실제 앱의 처리 결과는 별도로 확인해야 한다.

## 영상 녹화

"선택한 창을 5초 동안 5fps로 녹화하고 변화를 알려줘" 또는 "관리형 브라우저를 3초 녹화해"처럼 요청한다. 선택 창은 `Window capture / video`, 관리형 브라우저는 `Managed browser` 권한을 사용한다. 마우스/키보드 권한은 필요 없다.

- `desktop_record` / `browser_record`는 1~30초, 1~15fps, 긴 변 최대1280px의 **무음 MP4**를 저장한다. 음성·마이크 수집이나 보호된 영상 우회는 지원하지 않는다. 별도 인코더 설치 없이 OpenCV의 MPEG-4 코덱을 사용한다.
- 선택 창 녹화는 매 프레임 해당 HWND를 직접 렌더링하며 가림·포커스 변경만으로 중단하지 않는다. 위에 겹친 다른 창은 영상에 담지 않는다. 창이 닫히거나 최소화되거나 완전히 화면 밖으로 나간 경우, 렌더링이 실패하거나 제한 시간을 넘긴 경우, 인코딩 프레임 크기가 달라진 경우에는 중단한다. 중단 전 프레임이 있으면 재생 가능한 부분 MP4와 대표 프레임을 보존하고 목록에 `partial`로 표시한다. 아직 한 프레임도 저장하지 못한 경우에는 파일을 만들지 않는다.
- 모델은 동영상 파일 자체가 아니라 시간 표시가 있는 **최대4장 대표 프레임을 합친 이미지 한 장**을 다음 요청 한 번만 본다. 빠른 움직임이나 프레임 사이의 사건을 모두 분석하는 기능은 아니다. 전체 영상은 사용자가 파일로 재생한다.
- 캡처 처리가 목표 fps보다 느리면 이전 프레임을 반복해 재생 시간을 맞춘다. 메타데이터에 저장 프레임 수·재생 길이·실제 경과 시간을 남기며, 정밀 실시간 녹화는 보장하지 않는다.

## 검증
